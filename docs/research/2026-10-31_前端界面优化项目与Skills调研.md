# 前端界面优化项目与 Skills 调研

核对日期：2026-10-31。范围：现有大师赛档案网站的视觉、交互、响应式及相关质量验证。本文是候选工具与实施建议，不代表已经安装工具、实施改版或验证其实际效果。

## 结论

建议保留现有深色薄荷绿方向，以中文阅读、数据层级和手机查阅为优化重点。先选对局详情页做桌面、手机样板，确认后再推广到首页、榜单和选手页。

工具组合建议：以 Impeccable 做定向设计迭代，以 Vercel web-design-guidelines 复核界面质量；有明确性能瓶颈时，再参考 Vercel React Best Practices。UI/UX Pro Max、Anthropic frontend-design 用于需要探索视觉方向的阶段。这个排序是结合项目现状的判断，不是工具效果的实测排名。

## 项目现状与判断边界

以下为本次读取源码确认的现状：

- [package.json](../../website/web/package.json) 声明 Next.js 16、React 19、TypeScript 5.9；没有 Tailwind 或完整 UI 组件库依赖。
- [layout.tsx](../../website/web/src/app/layout.tsx) 依次加载 globals.css、interface.css；各页面还使用 CSS Modules。现有主题已经定义背景、面板、边框、正文、辅助文字及薄荷／金／红等颜色变量。
- [globals.css](../../website/web/src/app/globals.css)、[interface.css](../../website/web/src/app/interface.css) 和页面样式存在多层字号、间距及组件样式覆盖。优化涉及这些区域时，应核对最终生效样式，并就地收敛；不能只据基础规则中的小字号断言页面目前不可读，也不必先重写全部样式。
- 榜单已有固定表头、固定排名／选手列及横向滚动工具；比较表桌面宽度设为 3340px。优化重点应是分组辨识、当前位置和移动端查阅成本，不能把已有能力当作待新增能力。
- 对局列表已有 GET 参数筛选、分页与展开阵容；指标样本使用原生 dialog；主页已有 CSS 绘制的十二座位图。应先复用这些机制。
- [check_publication.py](../../website/check_publication.py) 已使用 Playwright 检查 1440×1000、390×844 页面、整页横向溢出、图片解码及页面错误，并支持保存截图；可复用现有验证入口。
- 对局档案必须继续消费共享 timeline，遵循[对局信息呈现规范](../10_对局信息呈现规范.md)。调整排版、导航和折叠方式时，保留日夜、票轮、事项顺序、必要待核信息和证据关联。

本次默认本地 3000／8000 端口未发现运行中的网站服务，因此没有进行实时浏览器截图、性能测量或交互验收。下述页面方向是源码基础上的候选方案，不是已经确认的视觉缺陷清单。

## 页面可以怎样优化

| 区域 | 候选优化方向 | 可检查的结果 |
| --- | --- | --- |
| 全站基础视觉 | 在已有变量上补齐必要的字号、间距和圆角约定；统一标题、正文、辅助说明、表单和按钮；只收敛本轮涉及的重复覆盖。 | 同类组件跨页一致；中文长文本、数字和说明层级清楚；窄屏不依靠缩小全部文字解决拥挤。 |
| 对局详情页 | 强化赛季／日期／版型／结果的概览层级；统一座位卡中的座位号、姓名、物理底牌与个人阵营；优化日夜标题、事件正文、票表的视觉关系。长页面可评估阶段锚点。 | 能快速找到某天、某轮票型和某个座位；DOM／视觉顺序符合共享 timeline；特殊角色状态与必要待核信息仍可识别。 |
| 榜单 | 在现有固定表头和固定列上，改善指标组标题、数值对齐、行定位与计算明细的展开层级。若手机横向浏览仍成本过高，再比较“指标组切换”等备选方案。 | 横向移动后仍知道当前选手和指标组；分子／分母及样本入口可发现；排序、并列和统计口径保持正确。 |
| 对局列表 | 比较关键词、赛季、版型与更多条件的优先级；让当前条件、结果数量、清除与分页更容易理解；延续已有阵容展开。 | 常用检索更容易完成；筛选 URL 可分享，返回列表后能理解当前范围；键盘和手机均可操作。 |
| 选手页 | 改善头像／姓名、统计范围、核心指标和对局记录的层级；统一样本弹窗、排名弹窗的标题、筛选和关闭操作。 | 能区分统计范围、指标结果和样本明细；长姓名／缺照片情况下布局稳定；弹窗焦点与关闭行为正确。 |
| 首页 | 保留赛事档案特色和十二座位意象，优化首屏比例、主入口、近期比赛与赛季入口之间的优先级。 | 首屏能理解网站用途并进入对局／榜单；主次操作明显；手机装饰不遮挡内容。 |

视觉方向首选“赛事数据档案”：保留深色与薄荷强调色，收敛装饰，提升中文排版和信息分组。若用户希望品牌变化更大，可另做“赛事编辑部”方向样稿，用更强的标题和选手图片组织首页；在方向确定前不增加主题切换系统。

## 建议实施顺序

1. **建立真实页面基线。** 启动现有网站，选首页、对局详情、榜单、选手页的代表内容；保存桌面与手机截图。界定本轮要改善的阅读或操作问题。
2. **确定一个样板。** 优先对局详情页，用真实内容制作桌面、手机两种布局；比较字号、间距、卡片、票表和阶段层级，形成可审阅结果。
3. **落实局部视觉约定。** 复用现有变量和组件；在本轮影响范围内收敛覆盖，保证语义和交互正确。
4. **推广到其他页面。** 依次处理榜单、选手页、列表和首页，每页围绕一个可观察问题验收。仅在具体组件出现能力缺口时引入依赖。
5. **完成对应验证。** 运行前端 typecheck、build；复用相关浏览器检查，检查手机、键盘、弹窗、长姓名、空结果与图片。对局流程或票型结构发生变化时，补做相关语义回归；不因纯样式调整批量复核赛事数据。

性能测量在生产构建下进行。若要采用 Core Web Vitals 作为后续目标，官方“良好”阈值为 LCP≤2.5 秒、INP≤200 毫秒、CLS≤0.1，按桌面／手机分别看真实访问的第 75 百分位。Lighthouse 的普通导航测量不能直接给出真实 INP；本次未测量这些指标。[Web Vitals 官方说明](https://web.dev/articles/vitals)
