# 对局档案与数据库

本页说明正式事实与存储结构。具体写入范围、备份、各季命令和回执验收统一按[全流程第五步](01_赛季数据全流程.md#第五步核对后写入数据库)执行；证据判断查[字段规范](02_字段证据与交叉复核规范.md)，版型差异查[规则与模板](05_版型规则与模板维护.md)。

## 三层数据

| 层次 | 入口与用途 |
| --- | --- |
| 原件与复核旁证 | 来源manifest、原始文字／图片、`data/extractions/`、审计补丁与用户确认；保留证据、推导、版本和未决项 |
| 正式对局 | `data/games/{season}/{game}/` 的 `dossier.json`、`voting.json` 及实际存在的旁文件；按赛季适配写入本机JCMS业务表 |
| 网站发布 | 从磁盘正式JSON及旁证生成 `masters_web` 不可变快照，在事务内切换活动release；不直接从JCMS业务表读取事实 |

正式档案保存规范化事实，证据与审核过程在旁证中保存；通过来源、文件路径和哈希关联。候选 `*.candidate.json`、原始复核输入和正式文件分开，构建时应用已有补丁，不通过覆盖机器起点抹掉判断过程。

## 单局正式文件

| 文件 | 内容 |
| --- | --- |
| `dossier.json` | 本局日期、季期、局次、版型、座位、实际身份、个人阵营、日夜固定事件及胜方 |
| `voting.json` | 首次报名／警下、各日警徽与放逐票、PK／技能重投、逐人投向及覆盖缺口 |
| `endgame.json` | 独立拍刀等终局记录，与普通夜刀分开 |
| `rule_derivations.json` | 前置共用规则的存活、票权、技能资源与合法目标、before/after及来源哈希；按[通用规则推导](07_通用规则推导.md)生成和消费 |
| `supplemental.json`、`vote_control.json`、`formal_context.json` | 按现有赛季契约保存额外现场事件、票力／票权旁证和正式范围上下文；不是要求所有季补造同名文件 |
| 导入收据 | 来源版本、规则哈希、事务结果与内容摘要，记录在相应回执／报告中 |

物理身份 `role`、个人胜利阵营 `faction`、规则中的淘汰边分别理解。榜样、机械学习、傀儡、面具不改底牌；原操作目标与实际效果分开。未知、空过、不适用和规则禁止按当前文件与模板契约编码，不全局替换枚举。

归档的 `round` 和 `phase`、投票关联的白天编号及原始证据称呼保持原值。日夜展示名称与排序统一按[呈现规范](10_对局信息呈现规范.md#阶段与统一阅读顺序)映射；导出复核结果同时保留原轮次与展示称呼。

## JCMS业务表

| 表 | 保存内容 |
| --- | --- |
| `people`、`person_aliases` | 统一人物与有依据的别名；人物没有固定的选手／解说类别 |
| `game_details`、`game_seats`、`game_staff` | 对局信息、座位身份及学习结果、本局解说与法官 |
| `game_rounds` | 实际发生的轮次，不为资料缺失补造一轮 |
| `board_templates`、`board_event_slots` | 版型与每夜／每天固定归档槽位 |
| `game_event_records`、`game_event_targets`、`game_event_votes` | 固定事件、行动目标、槽位内票型及发言顺序等结构化字段 |
| `game_event_effects` | 毒药反弹实际死者、技能刀穿盾等效果，与原目标分开 |
| `game_formal_annotations` | 现有`review_context`类型下的`shared-rule-derivations`保存共用规则推导及依赖，与规范化事件同事务写入 |
| `game_sheriff_registrations`、`game_ballots`、`game_ballot_choices`、`game_voting_days` | 独立投票文件中的报名、每一真实票轮、逐人票型及覆盖；当前查询视图为 `current_game_votes` |
| `sources`、`artifacts`、`game_files` | 原来源、文件登记及本局使用的当前文件关联 |

精确列定义以[数据库迁移](../db/README.md)为准。早期 `game_revisions`、`extraction_runs`、`transcription_runs`、`evidence_links` 等表保留历史；通用正式录入不从旧候选表猜事实。S21专项核实层由 `import_s21_formal.py` 转成当前正式结构，原专项证据继续保留。

2026-10-30人工槽位复核反馈由 `scripts/import_manual_slot_review.py` 校验原页指纹、12席身份、档案SHA与修改前值。`--apply`归档原始JSON至 `data/extractions/shared/manual_slot_reviews/`，并生成各局 `slot.reviewed.json`；S21/S23正式重建在推导规则前应用它，保留用户原备注和规范化结果。后续反馈仅替换同坐标结论，其他结论及上一批来源保留。终局未进入的行动记为不可用，不能按主动空过处理。首批撤回的DN-084已由第二批重新确认为第一天夜晚自守9号，首夜学习不变；第二批S23旧页反馈仅在核对身份、字段及既有九尾狐接刀映射后沿用，不恢复失效普通狼刀。应用与验证见[二次复核回执](../data/reports/shared/槽位人工复核二次应用_20261030.json)。

## 导入与验证边界

- 先登记本局真实来源与至少一个现存音频、字幕或转写入口；纯字幕资料无需补下载音频。
- `game_records.py` 按事务更新当前单局，重复导入不应新增重复对局或事件。严格校验与S22批处理的 `allow_incomplete=True` 是不同入口，后者允许必要未知，但仍校验已知角色和动作。
- `dossier.json` 内的槽位票型不能代替完整 `voting.json`。S22单局 `import-edits` 现在将已有投票文件的派生票权与日夜记录同事务导入；目录没有投票文件时不造票轮。各季入口见第五步。
- S23沿用正式快照prepare、预检及事务导入；S21复用已核专项记录的正式适配。结构检查、事务成功和人工事实确认分别报告。
- 按需修改JSON或补丁后，只重查实际受影响的字段与直接依赖；必要构建不会自动把整季标为重新核实。

业务表不直接承载网站活动版本。发布全保留季、同步悍跳及照片、回退与验收见[第七步](01_赛季数据全流程.md#第七步发布所有保留季及新季照片)、[第八步](01_赛季数据全流程.md#第八步验收交付并确定下次续跑点)和[网站手册](../website/README.md)。
