# 对局数据库与版型模板

2026-10-22 按用户新口径更新。当前入口为 `scripts/game_records.py`，单局数据为 `dossier.json`，数据库使用本地 PostgreSQL `jcms`。

单局示例已经完成。S22 的13类固定槽位模板已建立，批量入口为 `scripts/batch_s22.py`；操作、复核与续跑见 [S22 批量处理与复核](11_S22批量处理与复核.md)。各版型规则、首夜/后续夜序和特殊判定见 [版型规则与夜间顺序](10_版型规则与夜间顺序.md)，其中区分官方规则图、项目确认及尚未回听的录像候选。未确认夜序的模板留空 `wake_order`，归档槽位排列不表示法官睁眼顺序已经核实。

## 一局的数据

| 表 | 保存内容 |
|---|---|
| `people`、`person_aliases` | 统一人物姓名与账号别名，人物没有固定的选手/解说类别 |
| `game_details` | 本局日期、季期、局次、版型和胜方 |
| `game_seats` | 座位、人物、实际身份、阵营和机械狼学习结果 |
| `game_staff` | 本局解说、法官，各自关联同一份人物表 |
| `game_rounds` | 实际游戏轮次 |
| `board_templates`、`board_event_slots` | 版型及其每夜、每天固定槽位 |
| `game_event_records` | 每轮每个槽位的动作、行动者、结果和发言起点/方向 |
| `game_event_targets`、`game_event_votes` | 操作目标、逐人票型 |
| `game_sheriff_registrations`、`game_ballots`、`game_ballot_choices`、`game_voting_days` | 整局转写补录的警下名单、逐日警徽/放逐票、PK各轮及覆盖缺口；查询用 `current_game_votes` |
| `game_event_effects` | 毒药实际死亡者、反弹者或技能刀穿盾，与原始操作目标分开 |
| `sources`、`artifacts`、`game_files` | 来源、路径、类型、大小、哈希，以及本局选择使用的当前源文件 |

其人、桃子均为人物，可以在别局作为选手。豆儿啵和辉少是已知常见法官姓名。场上座位以首局自我介绍及用户确认建立，不按微博图片序号补位。JY在场时固定为7号；本局9号翼风、11号申屠、12号陈俊洁也已由用户确认。

## 固定事件

机械狼通灵师夜间按本局角色操作展示顺序记录：守卫 → 狼人 → 女巫 → 猎人 → 机械狼 → 通灵师。女巫拆分解药、毒药，机械狼拆分带刀确认、夜间技能，共8个槽位。

每天固定11个槽位：上警名单、警长投票、警长结果、夜间出局、猎人开枪、警徽、白天发言顺序、放逐投票、放逐结果、狼人自爆、机械狼白天技能。技能槽位表示该天的技能记录，不假定技能一定发生在其排列位置。

模板定义在 `config/board_templates/mechanical_wolf_seer.json`。每个实际轮次重复同样的8夜间槽位、11白天槽位，本局3轮共57项；未发动也保留，未知、未发动和不适用分别记录。其他版型在同目录的独立模板中定义角色与槽位，盗宝大师保留动态角色池，邻里傀儡的傀儡标记不算第13张身份牌。

事件字段固定为：`slot`、`action`、`actor`、`targets`、`result`、`start_seat`、`direction`、`votes`、`random_point`、`speech_scope`、`availability`、`effects`。`availability`记录机械技能的发动条件，`effects`记录可由规则确定的结算；二者自动计算并校验，不加入自由描述。描述由这些字段和本局身份自动生成：

- 第一天白天12号狼人自爆
- 第三天白天3号狼人自爆
- 第一天白天随机点数3，从4号平民开始顺序发言
- 第三天白天随机点数11，从11号平民开始顺序发言
- 第三天白天7号猎人开枪带走8号机械狼

号码后紧跟实际身份，不添加“报查杀后”“认狼”“实际发言至”等自由叙述。发言顺序保存随机点数、警上/白天范围、实际起点和方向；随机点数对应的座位不参与本轮发言时，沿方向跳到下一位。本局第一天3号未上警，点数3对应的实际起点为4号；第二天没有发言环节。

猎人状态根据女巫、机械女巫用毒情况计算，被毒则不能开枪，未被毒则可以开枪，普通狼刀不禁用猎人技能。机械女巫的毒药即使在猎人睁眼步骤之后记录，也影响本夜最终技能状态。之前轮次已出局的猎人不再参与后续夜间操作。通用规则保存在 `config/game_rules.json`，验证器拒绝与规则矛盾的发言起点或猎人状态。

## 机械狼技能与结算

每局只允许一只机械狼、一个学习结果；学习目标的实际身份必须匹配学习形态，不能跨形态使用技能。

| 学习形态 | 固定记录位置 | 最早可用时点与条件 |
|---|---|---|
| 机械双刀狼 | 夜间机械技能；普通刀另记在狼队击杀 | 学习后下一夜起，并且其他狼人全出局、机械狼带刀后；技能刀无视守卫的盾 |
| 机械通灵师 | 夜间机械技能 | 学习后下一夜起查验 |
| 机械女巫 | 夜间机械技能 | 学习后下一夜起用毒 |
| 机械守卫 | 夜间机械技能 | 学习后下一夜起守护 |
| 机械猎人 | 白天机械技能 | 学习后紧接着的白天起；中毒不能开枪 |
| 机械平民 | 保留夜间、白天槽位 | 无技能分支 |

机械双刀狼的接刀限制只适用于该形态，其他技能形态不等待普通狼人全出局。本局第2、3夜仍有普通狼人在场，所以机械双刀技能记录为“尚未带刀，不能发动技能刀”。普通狼刀和技能刀各自记录一个目标；穿盾仅应用于技能刀。穿盾记录本身不代替全部死亡原因判定，夜间实际出局名单单独保存。

夜间单独保留`mechanical_knife_status`带刀确认槽位。已知完整身份、出局事件时，直接从上帝视角计算带刀时点，并校验本夜确认；不依靠猜测玩家发言。本局三夜均记录“8号机械狼未带刀”：第1夜3、6、12号狼人均在场，第2夜3、6号狼人仍在场，第3夜3号狼人仍在场。3号白天自爆前8号已出局，因此本局没有实际带刀夜。

女巫毒药命中机械守卫盾时：`targets`仍保留用毒目标，`effects`写入`poison_reflected`、`intended_target`（原目标）、`dead_seat`（女巫）、`shield_actor`（机械守卫）。原目标不因这瓶毒药死亡，夜间出局名单必须包含女巫；猎人是否中毒按`dead_seat`判断。盾的实际目标未知时，结算保留未知，不把原目标直接当死者。机械女巫与机械守卫不能同局共存，不建立二者同时用毒、反弹的场景。

本轮取得的 [官方规则图](../data/raw/rules/weibo_5228857471013279/rule_02.jpg)已明确：机械猎人是**出局时**发动技能，中毒不能发动；机械狼不与三名狼人见面且不可自爆；通灵师查验机械狼反馈其模仿对象身份。机械女巫图中只写次夜起毒杀，没有明确解药，当前不新增解药动作。上述新核对结论先记入规则文档；本轮没有改动运行中的验证器或已完成示例。

## 当前入口与早期试验

当前业务数据不保存证据、完整转写片段、版本或审核状态。转写文件保留在磁盘，作为源文件登记一个当前入口；不再逐段导入转写库。

早期 `game_revisions`、`extraction_runs`、`transcription_runs`、`evidence_links` 等表及 `dossier.v1.json` 保留为试验历史。通用正式录入不向这些表写数据，也不从旧候选JSON读取对局事实；S21专项核实层继续作为已核来源，由 `import_s21_formal.py` 转成当前正式结构。

```powershell
.\.venv\Scripts\python.exe scripts/database.py migrate
.\.venv\Scripts\python.exe scripts/game_records.py data/games/S22/2026-06-25_g03_BV1yt7v6QE3Q/dossier.json
.\.venv\Scripts\python.exe scripts/database.py catalog people
```

导入在一个事务中更新本局当前数据，相同JSON重复导入不会增加对局或事件数量。

批量入口显式使用 `allow_incomplete=True`：未知姓名、身份、阵营、法官和局次可为空，没有明确轮次时不虚构一轮。已知角色仍检查配置上限，事件检查版型槽位、合法动作、目标和已知行动者身份；资料不全时不套用依赖完整身份的机械技能推导。直接使用 `game_records.py` 的默认严格校验保持不变，原已确认示例继续受保护。

迁移 `008_batch_game_records.sql` 允许上述空值与鬼魂新娘第三阵营。入库收据、失败原因、复盘文字和人工复核状态保存在 `data/games/S22/` 与 `data/reports/`，不加入业务表。每局事务失败会回滚旧记录；修改 `dossier.json` 后用 `import-edits` 重新入库，再用 `mark-reviewed` 记录实际完成的人工复核。

正式对局的主来源指向本局录像对应的来源记录；关联文件可为音频、字幕或转写。纯字幕先用现有 `database.py import-media <manifest>` 登记原件，再按赛季入口导入；不要求为此补下载音频。S21入口及事务范围见[第五步](02_采集与座位姓名身份核实.md#第五步核对后写入数据库)。
