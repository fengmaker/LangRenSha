## 1. 当前模型与准确率

当前实际组合是 `faster-whisper 1.2.1 + multilingual Whisper base + CPU INT8`。faster-whisper 是推理实现，Whisper base 是所用权重；不能把引擎名称当作最高精度模型的名称。本次选择 base 是为了验证音频采集和本地转写流程，尚未完成正式模型选型。

已有样本出现专名、角色术语和座位数字错误，因此目前只能用于生成候选。尚无人工逐字真值集，不能报告“准确率 95%”等数值，也不能把提取出 12 座角色候选称为 12 座全部正确。

用户最新决定：先用现有 base，已完成这条样板的全文转写；人工复核关键事实和用时后，再决定是否升级。只有出现明确瓶颈才比较当前基线、[Whisper large-v3](https://huggingface.co/openai/whisper-large-v3)、[Qwen3-ASR-1.7B](https://github.com/QwenLM/Qwen3-ASR)。两者是候选，不宣称任何一项在本赛事绝对领先。本轮未安装或运行新模型。

评测先人工制作约 30—60 分钟的小样本，覆盖自我介绍、清晰发言、多人重叠、票型播报、法官终局复盘与解说。该时长是初步评测设计，不代表已足够推断全赛事表现。

分别测中文字符错误率、昵称/术语准确率、座位与票数准确率，以及整局 12 座配置、个人结果能否全部对应。身份和结算真值应从明确揭晓/结算材料建立，不能用另一份机器转写作为真值。校对后的数据也不能回算为模型原始准确率。

优先提升“座位—昵称—角色—结果”的正确性，而不是让摘要写得更流畅。两个模型说法相同也不自动成为已核验事实。详细一手核验见[中文转写模型选型核验](中文转写模型选型核验.md)。

## 2. 字幕应当先于重新转写

建议先探测平台已有的字幕轨。若有合适且可访问的人工/AI字幕，下载带时间轴的文本；仍需校对专名、角色和数字。只有字幕缺失、无法取得或质量不合适时，再对音频运行 ASR；也可以只对缺失或争议片段重新转写。

| 类型 | 处理方式 |
| --- | --- |
| 平台外挂字幕 | 从播放器返回的可用字幕轨获取原始 JSON，保留时间戳及来源 |
| 平台 AI 字幕 | 若作为可用轨返回，可以直接获取；保留平台标记，不因为来自平台就视作人工真值 |
| 烧录在画面上的字幕 | 没有独立文本轨时需要取帧 OCR，音频脚本不能直接取得 |
| AI 总结/视频小助手摘要 | 可辅助定位，不代替逐字稿、身份揭晓或结算 |
| 弹幕与评论 | 只能作为寻找片段和纠错的线索，默认不作为事实来源 |

yt-dlp 当前 B 站源码使用 `/x/player/wbi/v2`，读取 `subtitle.subtitles`，并识别 `need_login_subtitle`。可返回字幕就有机会直接下载，不需要先下载视频。其 B 站字幕归入 `subtitles`，不能简单以为通用 `--write-auto-subs` 选项会为本来无轨的视频现场生成 AI 字幕。参见[一手源码](https://github.com/yt-dlp/yt-dlp/blob/master/yt_dlp/extractor/bilibili.py)和[字幕与登录条件核验](B站字幕与登录条件核验.md)。

## 4. 视频只按需读取，不默认长期保存整段

建议长期保存压缩原音频、关键帧、字幕/转写、结构化记录和来源证据。完整视频默认不入长期存储。OCR 得到的文本应与原图同时保留，不能只有识别结果。

取视频帧仍要传输并解码目标附近的视频数据，不能做到只传输一张 JPEG 的全部输入。服务器支持字节范围请求、媒体支持定位时，可以跳到目标附近读取少量视频；解码通常也需要前一个关键帧附近的数据。是否有效必须针对实际流验证，不能承诺任意录像都只读固定大小。FFmpeg HTTP 协议支持寻址相关选项，见[官方文档](https://ffmpeg.org/ffmpeg-protocols.html#http)。

后续关键帧采集器应设置每次传输上限、每局任务上限和总缓存上限；不支持有效定位或达到上限时停止并报告，不悄悄下载整段。只有个别争议片段需要临时短视频缓存，完成核验后按明确的保留策略处理。

### 优先抽取的画面

1. 当晚完整阵容或座次总览：核对昵称及座位，不依赖人脸猜姓名。
2. 本局板子/配置图：核对角色构成和规则版本。
3. 终局身份总览、角色揭晓：如画面确实提供，则核对座位与角色。
4. 最终结算和积分画面：核对个人结果、计分资格、该阶段积分。
5. 音频有歧义的投票/出局片段：仅为需要的事件补帧。

先从字幕/ASR定位“本局配置、身份揭晓、复盘、积分”等片段，再在附近抽多张画面；不每秒全片截图，也不固定假设每局最后一分钟就是结算。

OCR 适合先读名字、座位、角色和分数；视觉模型帮助理解版面和对应关系；有冲突则人工复核。保存 BV、CID、媒体秒数、画面尺寸、图像哈希、文字区域和识别版本。

### 存储估算

64—128 kbit/s 音频每小时约 28.8—57.6 MB（十进制）。本次 65 分钟样本约 49.6 MiB，约 52 MB。假设每局保留 20 张、每张 300 KB 的 JPEG，另需约 6 MB；实际大小取决于分辨率和画面。

100 小时压缩音频约 2.9—5.8 GB，另加关键帧和模型。模型权重是一次下载复用的固定成本；不应为每条视频复制一份。转写时当前程序会在内存中解码音频，不把完整 WAV 长期落盘。

## 6. 资源采集优先级

| 优先级 | 资源 | 用途与边界 |
| --- | --- | --- |
| P0 | 官方赛季规则、正式积分/更正图（若已发布） | 确认逐季计分、决赛重置、计分局和最终名次；保留规则生效范围 |
| P0 | B 站官方合集、单条元数据、分 P 与 CID | 建赛季/场次/对局候选目录和稳定来源定位；标题不是最终事实 |
| P0 | 已有可访问的字幕轨，包括平台 AI 字幕 | 节省重新转写时间与成本；仍保留错误和来源标记 |
| P0 | 官方阵容/板子公告及其原图 | 建嘉宾昵称词表、规则候选、选样目录；不代替实际座次 |
| P0 | 每局座次、身份揭晓、结算关键帧 | 核对 L1 的核心结构化事实 |
| P1 | 每局独立压缩音轨 | 补字幕缺失、复盘和事件；用更强 ASR 处理重点片段 |
| P1 | 官方复盘、规则解释、明确更正 | 解决歧义；区分正式裁定与解说观点 |

| P2 | 粉丝剪辑、评论、弹幕 | 仅作定位和问题线索；首版不批量采全部评论 |

## 7. 建议的下一步顺序

1. 先补正常登录后的字幕探测，确认样板中人工/AI字幕的实际可用性。
2. 抓取首批对应日期的官方微博阵容、规则和积分资料，建立名字与规则字典。
3. 实现有传输/缓存上限的关键帧读取，先验证一局的座次、身份揭晓及结算。
4. 先用现有 base 人工复核样板；仅在关键事实错误或复核成本成为瓶颈时，比较候选模型。
5. 将上述结果融合为待复核候选，再发布 L1；稳定后才扩大整季批次。

优先做互相补充的来源采集，降低对单次 ASR 或单张 OCR 结果的依赖。
