# 京城大师赛数据网站：V1.0 最终实施方案

> 历史参考：本文件保留此前方案与试验过程。当前执行范围以 [项目入口](../../../README.md) 和 [三步路线](../../01_项目路线.md) 为准；当前只推进第一步原始媒体采集。旧文中的“下一步”不作为当前任务。

版本：评审修订版 1.3（本机数据库与单视频样板落地）  
修订日期：2026-10-20  
产品定位：京城大师赛非官方赛事档案与统计网站。  
首版目标：让经过核验的比赛能够持续录入、复核、发布、更正，并让读者从统计结果追溯到具体对局和原始证据。

本方案替代原文中的实施安排。它是一份开发和数据运营基线；目前已实现本机 PostgreSQL 与一条视频的音轨、全文转写及候选入库，公开网站和经过人工核验的历史数据库尚未建成。实际命令及状态见[数据库与单视频完整流程](数据库与单视频完整流程.md)。

当前执行重点：先完成人工复核这条样板，继续使用现有 Whisper base，观察关键事实错误及复核用时后再决定是否比较其他模型。B 站、微博采集均支持匿名和显式 Cookie 两种模式，真实登录路径仍待用户正常登录后验证。

## 一、原方案评审结论

原方案值得保留的部分：明确赛事边界；重视一手来源；未知值不冒充事实；选手使用稳定身份；AI 标注先审核；不把官方积分和网站指标混为一谈。

需要修改的主要问题如下。

| 原方案的问题 | 实际影响 | 本版处理 |
| --- | --- | --- |
| 同时追求全历史索引、当前赛季更新、详细投票、夜间事件和排行榜 | 内容与工程范围叠加，首版很难完成 | 保留长期方向，拆成内部样板、公开首版、后续统计三步 |
| “决赛周 12 局”直接成为交付前提 | 尚未形成逐局核验清单，可能混入重播、表演赛或不同赛事阶段 | 先核验候选清单；12 局是建设目标，不是已证实的赛事总数 |
| 先做前台，再做录入和审核 | 数据链路的问题发现过晚 | 优先完成一条从录入到更正的完整流程 |
| 胜率、投票正确率没有完整分母及排除规则 | 同名指标可能算出不同结果，也可能误导读者 | 固定统计合同，限定适用规则和样本范围 |
| 用数据层级代替统计资格 | 一局有部分事件，不代表所有指标均可计算 | 数据层级、审核状态、各指标资格分别管理 |
| 只描述“审核后重算” | 无法解释草稿修改、旧版本保留、撤回后如何纠错 | 增加不可变发布版本、发布指针和撤回流程 |
| 以“20 余张表”代表完整设计 | 增加首版实现成本，仍可能漏掉真正的约束 | 按业务关系建模；投票和技能表随对应功能迁移 |
| 声称 SQL、HTML、ZIP、CSV 测试等已经交付 | 本次附件只有文字，不能证明这些成果存在或通过验证 | 全部改为后续交付物；收到文件后另行验收 |

**项目最重要的验收对象，是数据链路的可靠性与持续维护能力。**

## 二、产品范围与分期

### 2.1 服务对象与核心任务

- 观众：按赛季、日期、选手、板子寻找比赛，打开原始录像。
- 数据读者：查看选手在明确样本范围内的出场和胜负，理解统计覆盖范围。
- 维护者：不用修改代码，就能录入、复核、修正和发布比赛。

参考 HLTV 的信息组织方式，但使用适合狼人杀的数据模型与原创页面设计。

### 2.2 赛事收录边界

| 内容 | 处理方式 |
| --- | --- |
| 京城大师赛正式赛季正赛、正式决赛 | 收录，赛事阶段分别标记 |
| 后续新赛季 | 支持持续新增，不设置 S22 或 S23 的硬上限 |
| 赛季表演赛 | 收录索引、音频和可核验结果，单独标识；不计正式积分，默认排除于正式比赛统计 |
| 娱乐局、赛后自由局 | 不纳入首版对局库；原始录像含这些片段时保留媒体边界 |
| 小师赛、龙门赛、地方公开赛等其他赛事 | 不在本项目范围 |
| 6+6 等特殊赛制 | 先核实官方归属；允许独立建档，但规则适配前不进入普通 12 人统计 |
| 重赛、中止、取消、裁定无效局 | 保留可核实的档案和状态，按裁定决定统计资格 |
| 正式性质或规则无法确认的比赛 | 留在待处理区，不发布到正式赛事目录 |

“决赛”作为赛事阶段保存，不另外复制一份比赛。每一局只有一个稳定的比赛 ID。

2026-10-20 用户补充规则：赛季首周表演赛；19:00 开赛，前三局在 22:30 前结束时可有第四局；正赛第四局计分，表演赛及决赛周第四局不计分；决赛周积分清零并单独决定冠军；狼人胜 +1.5、好人胜 +1、双方负均 -1。用户已确认适用历史赛季需要逐季核实，因此这些是有来源的规则候选，不自动应用到所有赛季。完整记录和未知例外见[逐局采集规范与赛制规则](逐局采集规范与赛制规则.md)。

数据模型必须分别保存赛事阶段、局序、是否加赛、是否计分、积分阶段和各项统计资格。决赛周第四局不计分，不等于该局不存在。默认正式胜负统计选取适用范围内的计分正式比赛；可通过单独筛选查看已核验的非计分比赛，两类口径不能混称。

### 2.3 版本边界

| 版本 | 必须完成 | 不作为该阶段交付条件 |
| --- | --- | --- |
| V0.1 内部样板 | 至少 12 局候选索引；其中 3 局完成 L1 核验；录入、复核、发布、更正闭环；最小对局和选手页 | 全历史、排行榜、完整投票和夜间技能 |
| V1.0 公开首版 | 至少 12 局正式比赛完成 L1；六类公开页面；后台持续录入；基础统计；权限、备份恢复和上线验证 | 综合实力评分、全历史补齐、自动采集 |
| V1.1 | 先选 2—3 局做 L2/L3 样板；验证投票事件和时间轴，再决定扩展 | 所有板子的通用技能模拟器 |
| 后续版本 | 历史补档、符合样本条件的榜单、选手对比、官方积分展示、经验证的专项分析 | 在缺少依据时推断玩家水平或心理动机 |

数据维护按小批量推进：公开首版至少在上线时最近有可靠来源的赛季中，实际新增并发布一局，优先选择正在进行的赛季；如果当期来源不足，使用最近可核验赛季并注明原因。不能把“S23”永久写死为当前赛季。全历史索引作为持续运营任务，不阻塞首版上线。

## 三、首批数据与外部事实处理

### 3.1 首批选样

优先从 S22「曙光航纪」相关决赛录像中选样，同时为 S23「昆仑归墟」建立可持续新增的目录。

选样顺序：来源可靠且可访问 → 正式性质明确 → 座次、身份、结算可核验 → 规则资料可获得。优先验证常见规则，再加入特殊规则。

首批目标为 12 局，并不预设“四天各三局”已经得到证实。如果候选录像不足、重复或阶段存疑，记录原因，改用相邻日期可核验的正式比赛补足。

本次后续采集已从 B 站接口取得“曙光航纪”官方合集的 163 条候选索引，其中标题标记为决赛周的有 13 条，包含[8 月 19 日第四局—鬼魂新娘](https://www.bilibili.com/video/BV1tj8p6REfY)。12 条每天前三局与 1 条第四局应分别记录，不再把常规局数当作全部录像条目数。根据用户补充，决赛周第四局不计分；具体赛季适用性、逐局身份、胜负和积分仍须核验。目录条目不等于已核验对局。

### 3.2 事实与来源的边界

- 赛季名称、比赛日期、阶段和局数应分别有来源，不能仅凭一个宣传标题推断全部信息。
- 官方宣传或阵容单可证明排期，不能单独证明实际座次、身份和最终结算。
- 官方发布、后援会上传、个人剪辑和第三方统计分别标明，不能统一显示为“官方来源”。
- 搜索摘要只作为发现线索；未核对原始内容的项目保持待核验。
- 赛事日期与录像发布日期分别保存；不得用上传日期直接替代比赛日期。
- 原文提及的整理者及其数据，只有在具体取得使用许可后才进入导入计划；不假设已存在开放接口或授权数据集。

逐项核验结果见同目录的[来源核验记录](京城大师赛_来源核验记录.md)。未能核验的内容不作为本方案的确定事实或上线前提。

## 四、数据采集、复核与持续运营

### 4.0 来源与采集优先级

采用“官方规则/阵容/积分资料 + 平台现有字幕 + 对局关键帧 + 按需音频转写”的组合。先探测可访问字幕；需要登录时明确记录登录门槛，在正常登录后继续探测，不把空列表当作没有字幕。缺失或有歧义的内容再用 ASR，当前 Whisper base 只用于验证流程，正式选型需要项目样本评测。

官方微博正文和原图纳入来源台账；阵容预告不能代替实际座次，积分图与更正应绑定对应赛季和积分阶段。视频默认不长期整段下载，关键帧按目标时点读取附近数据，并设置传输及缓存上限。详细资源优先级和已实现/待实现边界见[采集资源优先级与升级方案](采集资源优先级与升级方案.md)。

### 4.1 数据层级

| 层级 | 内容 | 可支持的功能 |
| --- | --- | --- |
| L0 索引 | 赛季、场次、比赛日期、局次、阶段、板子、录像定位；无法确定的非关键项注明未知 | 经核验的赛事目录、录像入口 |
| L1 对局事实 | 完整座次、稳定选手 ID、开局角色与阵营、比赛状态、每位参与者的结算、对应规则版本和证据 | 出场、胜负、角色及阵营分布 |
| L2 投票 | 轮次类型、候选人、投票资格、投票对象、弃票/无效/缺失状态、必要的事件时点状态 | 限定规则的投票分析 |
| L3 事件 | 日夜、全局事件顺序、技能使用与生效、目标、死亡、身份或阵营变化及证据 | 复盘时间轴 |
| L4 解释性标注 | 悍跳、倒钩、关键发言等带定义和作者的观点 | 后续专题，单独展示，不混入客观事实 |

层级由已通过的完整性检查决定，不由录入者随意选择。L2/L3 的局部内容可以保存，但未满足完整性要求时不能宣称整局完整。

“达到 L1”也不自动等于所有榜单均可用：特殊赛制、无效结算等仍由指标资格规则排除。

### 4.2 每局标准流程

1. 建立稳定比赛 ID，核查同局是否已存在，确认赛事归属。
2. 绑定录像和规则来源，记录 BV/URL、分 P、可取得的 CID、视频起止秒数和上传者。
3. 创建草稿，填写座次、选手、开局角色与阵营、结算和证据定位。
4. 服务端检查完整性、重复值、规则配置与明显冲突。
5. 提交复核；退回时填写问题和理由，修改后重新提交。
6. 复核通过后，在事务中发布指定版本；前台和统计同步读取该发布版本。
7. 发现错误时创建修订草稿，旧发布版本保持不变；新版本复核后替换。
8. 严重争议时撤回公开版本，立即退出公开统计，保留内部记录与撤回理由。

审核状态主线为 `draft → submitted → approved`；被退回的提交标记为 `rejected`，保留原提交快照，修改时创建后继草稿。公开状态由独立的发布记录决定，不在同一个枚举中混用“审核通过”和“对外展示”。已提交、已批准或已发布的版本均不能原地改事实；修改需生成新草稿。

### 4.3 复核制度与证据

默认由另一位有权限的维护者复核。如果早期只有一人，允许录入者隔次重新核对，但后台保留“单人复核”标识，不能伪称双人审核。

胜负、角色、座次和赛事归属必须可追溯。证据可以共用一段结算画面，但要明确它支持哪些字段。证据至少包括原始链接、视频定位或文档位置、核验人、核验日期；AI 置信度不能替代人工核验。

来源冲突时保留不同说法及理由。明确的正式更正或最终裁定优先于早期播报；争议未解决的字段保持未知，受影响的指标暂停计算。

未知角色使用 `NULL` 并记录原因；未知结果与平局、无结果、弃票、无资格都应区分。不得把“没看到”记成“没有发生”。

### 4.4 导入与去重

- V1.0 支持后台手工录入，以及 L0/L1 的标准 CSV 导入；AI 只生成相同结构的待审核草稿。
- CSV 分为比赛、参与者、来源三个关联文件，使用稳定外部键；附模板、字段说明和错误示例。
- 导入分为上传、预检、差异预览、确认写入草稿四步。关键错误使相应比赛整体失败，不留下半局事实。
- 相同来源命名空间、外部键和内容摘要重复导入时不新增；内容变化进入更新差异，不覆盖公开数据。
- 同一 BV 可包含多局；同一局也可有无弹幕版、弹幕版和不同机位。录像 ID 不能充当比赛主键。
- 昵称只用于查找候选选手，不能自动合并；同名不同人允许存在。合并选手必须人工确认、留下日志并重新验证统计。

### 4.5 持续维护

后台提供待索引、待补证据、待复核、待更正、来源失效五类任务视图。每周至少安排一次队列整理，公开显示最近更新日期。

前三局实际记录录入和复核耗时，再决定更新承诺。历史补档量不得挤占当前赛季的约定维护能力。

## 五、数据库与规则设计

### 5.1 核心关系

```text
赛季 → 场次 → 比赛 → 多个数据版本 → 该版本的参与者事实
                 ↓ 当前公开版本
               前台与统计

选手 ← 参与者事实 → 开局角色、开局阵营、个人结算
比赛/数据版本 ← 证据关联 → 视频或规则来源
```

“场次”表达某一期某一天或某个独立赛段，不将日期直接作为唯一标识。跨午夜时保留赛事所属日期，精确时间用带时区时间存储，页面按 `Asia/Shanghai` 展示。

### 5.2 V1.0 必须实现的数据实体

| 实体 | 关键职责 |
| --- | --- |
| `seasons`、`sessions` | 赛季编号、名称、场次、日期与阶段 |
| `games` | 稳定 ID、局次、重赛关系、当前发布版本指针 |
| `game_revisions` | 该版本的比赛事实、阶段、加赛/计分资格、规则版本、数据完整性、审核版本与乐观锁 |
| `players`、`player_aliases` | 稳定选手身份、别名与身份合并记录；别名不作为全局唯一键 |
| `game_participants` | 版本内座位、选手、当场显示名、开局角色/阵营、结算计分身份、个人结果；计算基础分、调整项、官方积分独立并允许未知 |
| `scoring_periods` | 赛季内正赛和决赛周分别累计；决赛周清零不删除正赛历史；适用规则逐季绑定 |
| `roles`、`factions`、`rule_set_versions` | 角色和阵营字典、不可变规则版本、人数和角色配置、结算说明、适用统计分组 |
| `sources`、`game_sources`、`evidence_links` | 来源及比赛映射、录像片段、字段或事实级证据 |
| `reviews`、`publication_logs`、`audit_logs` | 复核、发布/撤回、更正原因和操作审计 |
| `import_batches`、`import_errors` | 导入摘要、差异、错误与重复执行记录 |
| 后台账号和会话 | 由选定认证方案维护，业务层保存权限角色 |

不以表数为验收目标。最终字段类型、枚举、索引和迁移必须在 Phase 0/1 中落成可运行文件。

### 5.3 必须保证的约束

- 同一版本中座位唯一、选手唯一；不支持的中途换人情况单独标记，适配前退出对应统计。
- 规则规定的人数、座位范围、角色构成在发布前校验；不把所有比赛硬编码成 12 人。
- 对局事实指向明确的规则版本；已使用的规则版本不能修改，规则变化新建版本。
- 所有子事实属于同一比赛版本，避免把不同版本的座次、投票或证据拼接。
- `published_revision_id` 必须指向本场已批准版本；用复合外键及受控发布事务保证。
- 发布、更正、撤回使用事务和并发检查，禁止“批准的是旧稿，发布的是新稿”。
- 公开数据不能通过普通删除连带消失；使用撤回、停用或受控合并，并保留历史。

可由数据库表达的非空、唯一和外键约束交给数据库。跨行人数、角色配额、证据完整性等交给服务端发布校验并在事务中复查，不能只依赖网页表单。PostgreSQL 对跨行/跨表 `CHECK` 的限制见[官方约束文档](https://www.postgresql.org/docs/current/ddl-constraints.html)。

### 5.4 特殊规则与后续扩展

个人胜负不能由“开局是狼人”或“最终哪一阵营获胜”一律推导。V1.0 保存有证据的个人结算，标明取自正式结算或依据哪版规则推导；无法可靠确定时不纳入胜率。

V1.1 再新增 `game_events`、`vote_rounds`、`votes`、`participant_state_intervals` 等表。状态区间同时支持角色和阵营变化；事件顺序使用独立序号，视频时间只是证据定位。警长竞选、退水、PK、重投、警徽移交和放逐须区分事件类型。

V1.0 为这些能力保留稳定版本与参与者 ID，但不提前实现通用技能引擎、所有事件表及全部规则模拟。

## 六、统计合同

### 6.1 共同准入条件

统计只读取当前公开、复核通过的版本；符合赛事范围、规则适用性和对应指标的事实完整性要求。重复录像不增加比赛数，中止、无效、争议和规则不明的比赛按指标规则排除。

每个统计结果都能查看：筛选条件、样本数、排除原因、统计更新时间、指标版本及计入的比赛列表。公开页面用“已发现 / 已建档 / 已完成 L1”表达收录进度；没有可靠赛事总量时，不宣称“历史完整率 100%”。

### 6.2 V1.0 指标

| 指标 | 计算口径 |
| --- | --- |
| 已核验出场 | 满足本指标条件的正式完成对局中，该选手参与的不同比赛数；不等于生涯总出场 |
| 胜、负、平局、无结果 | 按参与者结算分别计数，不把平局或无结果算作失败 |
| 胜率 | `胜 / (胜 + 负)`；明确标注不含平局和无结果；分母为零显示“—” |
| 角色出场及胜率 | 按开局角色分组，胜率仍按个人结算；明确显示“按开局角色统计” |
| 阵营出场及胜率 | 按开局阵营分组，使用个人结算；不与“某阵营在该板子的整局胜率”混称 |
| 角色/阵营分布 | 对应已核验出场中的占比，显示样本范围 |

最低筛选维度为赛季、阶段、板子/规则版本；全站总览必须标明跨规则汇总，不将它解释为公平的水平比较。详情和指标卡使用同一查询服务，避免各页自行计算。

示例仅用于验收，不能写入真实选手档案：某测试选手 2 胜、1 负、1 平、1 无结果，已核验出场 5，胜率 `2/3 = 66.7%`，胜率样本数为 3。

### 6.3 榜单与官方积分

V1.0 提供数据表和明确标注的排序，不设“最强选手”综合排名。样本不足时显示不足，不使用虚构数据填满榜单。

后续正式胜率榜默认要求当前筛选口径下至少 20 个胜负样本；阈值作为有版本的产品规则配置，不代表统计学上已足以判断能力。未达门槛者仍可查看档案，但不授予名次。

官方积分独立保存原始数值、规则版本、奖惩和来源。没有可靠积分来源时不展示；不从胜率反推积分，不把网站排序冒充官方排名。

用户提供的基础分规则已存入 `config/scoring_rules.user_reported.v1.json`。只有确认对应赛季规则及计分资格后，才能生成明确标注的计算分；仍要与官方公布分数比对。决赛周冠军仅按该阶段有效计分局的官方总分判定；并列处理规则未知时不得自行选出唯一冠军。

### 6.4 投票分析放到 V1.1

取消未定义的通用“投票正确率”。第一项可试行指标为：**好人放逐投狼率**。

定义：在已完整核验且适用的放逐轮次中，投票时属于好人阵营的玩家，其合法指向性选票投向当时狼人阵营的次数，除以其合法指向性选票总次数。

限定条件：警长竞选票不计；狼人玩家的票不适用；弃票、无资格、无效票分别展示；缺失票或当时阵营未知的轮次不参与该指标；PK/重投分轮记录；每次选票按一次计，警长权重另存，不混入本指标。对存在复杂转换的规则，只有当时状态完整可核验才开放计算。

同时展示有效样本、缺失/排除轮次与适用范围。该指标描述观众视角下的客观投票结果，不等同于玩家当时的信息判断能力。

## 七、技术方案与页面

### 7.1 技术基线

- 应用：Next.js + TypeScript，一个代码仓库、一个应用，前台和管理后台共享业务层。
- 数据库：PostgreSQL；本地、测试和生产保持兼容的数据库主版本。
- 数据访问与迁移：Drizzle ORM / Drizzle Kit，迁移文件纳入版本管理；复杂约束使用审查过的 SQL。采用生成并执行版本化迁移的流程，参见[官方迁移文档](https://orm.drizzle.team/docs/migrations)。
- 表单校验：共享字段定义，服务端再次执行完整业务校验；客户端校验只改善操作体验。
- 认证：采用维护中的 Next.js 兼容认证库，关闭公众注册，仅由管理员建立后台账号；具体版本在工程初始化时锁定并记录。
- 测试：覆盖业务规则的单元测试、真实 PostgreSQL 集成测试、少量关键端到端测试。
- 部署：一个应用服务和一个数据库；优先降低维护数量，按实际访问地区测试后确定部署区域。

首版不引入微服务、独立公开 API 产品、Redis、搜索集群、消息队列或机器学习评分。应用内部可以提供 Route Handlers 和服务函数，公开 API 文档与第三方接入延后。

应用服务、规则校验、发布工作流、统计查询分模块实现，避免所有逻辑堆在页面组件中。

### 7.2 公开页面

| 页面 | 首版必须具备 |
| --- | --- |
| 首页 | 站点定位、最近核验比赛、收录范围、更新日期和当前数据量 |
| 赛季列表/详情 | 阶段、场次、对局、该赛季已建档与已核验数量 |
| 对局列表 | 赛季、日期、选手、板子、阶段筛选，分页和可分享的 URL |
| 对局详情 | 录像入口、座次、开局身份/阵营、个人结算、规则版本、证据和更正记录 |
| 选手列表/档案 | 昵称与别名搜索、已核验出场、角色/阵营分布、样本范围和比赛历史 |
| 统计页 | 指标解释、样本数、筛选、数据表、来源下钻；数据不足时明确空态 |

六类页面共用移动端可用的布局。优先清楚的数据表、来源入口和筛选；电竞视觉风格不能降低文字可读性。测试数据仅存在于开发/测试环境，不能进入公开统计。

### 7.3 后台页面

后台必须提供赛季/场次管理、选手及别名管理、规则版本选择、录像索引、座次表格录入、缺失提示、CSV 预检、复核差异、发布/撤回、更正日志和任务队列。

12 人是常用录入模板，模板行数由规则人数生成。应支持复制上一局的人员名单，但角色、阵营和结果默认清空，避免把上一局身份带入下一局。

## 八、权限、发布一致性与运维

访客只能访问公开版本；录入员可维护草稿和提交；复核员可审核；管理员负责发布、撤回、身份合并及权限配置。同一账号可兼任角色，但日志记录真实操作人。

每一个写入入口都必须在服务端检查账号和权限，不能只隐藏按钮。Next.js 对 Server Actions 和 Route Handlers 的授权要求见[官方认证指南](https://nextjs.org/docs/app/guides/authentication)。

V1.0 统计直接查询公开版本视图，不先引入异步汇总。发布事务同时更新发布指针、公开数据版本号和日志；统计响应标记数据版本。首版统计与详情使用动态读取，避免旧缓存掩盖更正。确有性能需求后再加入带版本号的缓存或汇总表。

运维验收要求：

- 开发、测试与生产配置隔离，密钥不进入仓库；生产访问使用 HTTPS。
- 数据库迁移先在测试环境执行；上线有应用回退方案，数据库变更优先使用向后兼容迁移。
- 每日自动备份，至少保留最近 30 天，备份存于与生产故障隔离的位置；定期验证成功状态。
- 首次上线前和此后每月至少做一次独立恢复演练，校验比赛、发布版本、权限和审计记录。备份与恢复操作依据 [PostgreSQL 官方文档](https://www.postgresql.org/docs/current/backup-dump.html)。
- 首版恢复目标：最多损失 24 小时新增数据（RPO），4 小时内恢复基本查询和录入（RTO）；必须用演练验证，而非只写在文档中。
- 应用错误、数据库连接失败、发布失败和备份失败有可发现的记录与提醒；明确维护责任人。
- 来源失效时保留来源元数据和失效状态，不自行补写比赛事实；提供可用的纠错联系入口。

媒体处理基线：首版保存事实、来源元数据和原视频链接，不默认托管完整录像。第三方表格、图片等资源在使用前记录具体授权范围；“非官方”标识不能代替授权记录。

## 九、实施顺序、工作量与交付物

### 9.1 阶段计划

以下为一名有相关经验的开发者、需求基本稳定时的工程估算，不包含历史全集整理；实际排期在 3 局样板完成后修订。

| 阶段 | 工作内容 | 完成标准 | 工程估算 |
| --- | --- | --- | --- |
| Phase 0 口径与数据样板 | 数据字典、指标合同、来源清单；人工完整整理 1 局，选定共 3 局验证样本 | 关键规则和异常有明确处理；样板可被另一轮复核重现 | 2—3 人日 |
| Phase 1 最小完整流程 | 工程、迁移、账号、草稿、证据、审核发布、最小详情页和选手页 | 3 局完成录入、发布、更正；草稿不泄漏；迁移可重复执行 | 5—7 人日 |
| Phase 2 首版前后台 | 六类页面、筛选、别名、CSV 预检导入、任务队列、基础统计 | 使用真实已核验数据；从指标可查到比赛和证据 | 5—7 人日 |
| Phase 3 数据与上线验收 | 补足至少 12 局 L1；最近可核验赛季新增；质量检查、权限和恢复演练、部署 | 全部上线门槛通过 | 3—5 人日 |

工程合计约 15—22 人日。数据查找、观看、录入和复核单独计时；只有来源充分、工作量已测量时，才适合给出日历上线日期。

数据工作量估算采用实测公式：

`预计数据工时 = Σ(剩余各类对局数量 × 样板同类平均工时) + 来源核验 + 争议处理 + 返工`

预算先约定应用、数据库、备份、域名和维护工具的月度上限，再按实际服务商报价确定；不要把免费额度当作长期运营前提。

## 十、V1.0 上线验收清单

### 数据与指标

- [ ] 至少 12 局不同的正式比赛完成 L1，关键事实有证据，不靠重复录像凑数。
- [ ] 首批每局完成复核，并能说明实际复核方式；来源冲突均有处理记录。
- [ ] 在最近有可靠来源的赛季新增至少一局，完成全流程；优先当前进行中的赛季，无法选用时记录原因。仅记录阻塞不能代替实际新增验收。

- [ ] 公开显示收录范围、样本数、更新时间；未核验数据不进入正式统计。

### 关键业务检查

- [ ] 同座位、同局同选手重复、跨版本事实关联被拒绝。
- [ ] 未知角色保持未知；特殊规则不会被错误映射成固定好人/狼人结算。

```text
- 缺少真实样板资料时先交付可完成的架构与台账，明确缺口，不用虚构事实补齐。
```

Phase 0 结束应产出可审查的设计与事实缺口，而不是把整站代码量当作进度。之后以“3 局完整流程 → 至少 12 局公开首版 → 持续更新和深度统计”的顺序推进。
