## 三步主线

```mermaid
flowchart LR
  A[第一步：下载官方视频或音频] --> B[原始文件与来源登记]
  B --> C[第二步：模型转写文字]
  C --> D[AI 提取结构化候选]
  D --> E[第三步：核对和整理入库]
  E --> F[可查询的对局数据]
```

数据库是这三步的存储工具。第一步保存原始来源和文件信息，第三步才形成对局事实。第一步不依赖 ASR、AI 提取或选手身份核验。

## 第一步：采集官方原始素材——本轮 S22 已完成

**输入**：一条官方视频链接/BVID及其分 P；之后再扩展到经过选择的采集清单。

**过程**：核对投稿账号 → 取得视频元数据 → 下载独立音轨 → 校验文件 → 登记原始资料。当前先选音频以节约空间；完整视频及按需关键画面另行安排。

**输出**：

- 原始音频文件、官方链接、投稿账号、BV、CID、分 P。
- 原始标题、平台发布时间、平台时长和采集时间。
- 文件路径、字节数、SHA-256，以及音轨和起始解码检查结果。
- 可访问字幕轨则顺手保存；需登录、无可见轨或请求失败则如实记录。
- 本次采集的成功/失败报告，以及 PostgreSQL 中的来源和文件登记。

**本步通过标准**：指定样板来自已确认的官方投稿 UID；文件存在且大小/哈希正确；音频可打开、含音轨不含视频轨、时长与元数据相符、起始帧能解码；同一来源重复登记不增加重复来源/文件；遇到限制和不完整下载不误报成功。

这些检查不证明整局内容完整或音质无误，也不等于每句话已经识别；当前不把整段音频逐帧解码作为自动验收项。

样板已完成后，用户已明确要求采集 S22 全季。本轮推进官方《曙光航纪》合集全部媒体条目的音频与可用平台字幕，并做信息命名、原始登记和完整性筛查；不推进微博全历史采集、模型比较或网站开发。具体命令见[第一步操作手册](../../01_赛季数据全流程.md#第一步采集原始资料)。

## 第二步：转写文字，再让 AI 提取——当前试跑单条样本

这一阶段有两个连续动作，不把它们混成一次“自动识别所有信息”：

1. 语音模型将音频转写为带时间戳的文字。可取得的平台字幕也保留作对照；原始转写与人工修订分开保存。
2. AI 阅读这些文字，整理成固定格式的候选 JSON，每个事实附原文与媒体时间；读不出的地方留空并说明缺口。

当前保留 Whisper base 作为早期试验基线；新增 FunASR Paraformer + VAD + 标点 + CAM++ 单条试跑，按用户提供的工作流输出句级转写和发言归属候选。已有全文转写不代表完成了通用 AI 提取，也不代表具备可靠的说话人识别；批量处理等待人工 review。

当前优先把法官最终复盘单独提取并逐字核对，以其明确公布建立身份、夜间行动和结算候选。场上夜间仍可能有解说，分别记录对局阶段、说话者角色与内容类型。解说分析和玩家主张保留，但不代替复盘揭晓；完整逐人发言切分不是提取这些基础信息的前置条件。

### AI 最终需要提取什么

| 数据组 | 目标字段 | 边界 |
| --- | --- | --- |
| 对局信息 | 来源、比赛日期、赛季、阶段、局序、板子、人数、开始/结束位置 | 日期、阶段和板子标题只是线索，需要证据 |
| 上场人员 | 座位号、当场昵称、选手候选、实际身份、开局及结算阵营、个人结果 | 角色自称与真实身份分开；不能把悍跳当成揭晓身份 |
| 警徽票 | 第几天/第几轮、初选或 PK、投票人、目标、弃票、无投票资格及结果 | 未知票与弃票不同；重投单独记录 |
| 放逐票 | 日次、轮次、初投或 PK 重投、逐人投向、票重、放逐结果 | 警长票权与实投人数分开，不能只留一个总票数 |
| 发言 | 发言轮次/阶段、座位或待定说话人、起止时间、原始转写、校订文本 | 说话人聚类编号不等于选手姓名；保留重叠、缺失及不确定标记 |
| 对局经过 | 警长归属及变更、出局、明确技能事件、胜方、终局身份复盘 | 音频无法证明的事件，后续补画面或规则材料 |
| 整局复盘 | 按轮次排列的客观经过、关键票型、身份揭晓、结算与有依据的摘要 | 不能为了故事完整补造事件；解说推测与已发生事实分开 |
| 所有候选共有 | 来源 ID、转写版本、原文、媒体秒数、待核验状态、缺失原因 | AI 置信度不能代替核验 |

### 第二步也按层次做

先尝试基础字段：座位、昵称、身份、板子、胜负；之后逐项加警徽票、放逐票和发言轮次。完整逐轮复盘、每人全部发言和高准确率转写作为后续目标，需要另做样板验证。

当前尚未确定怎样可靠完成多人发言归属、重叠语音、专名、完整票型和跨轮次事件提取。先保留这些明确目标；不把“完美转写”当成已实现能力，也不让它阻塞原始素材的保存。

## 第三步：按版型整理为对局数据

**输入**：转写文件、微博人员排班和首局自我介绍。

**过程**：统一人物姓名 → 从首局自我介绍建立座位 → 对齐季期、局次与身份 → 按版型睁眼顺序填写每夜、每天固定槽位 → 校验并写入业务表。

**输出**：对局、统一人物、本局职责、座位身份、逐轮事件及逐人票型。当前业务数据不包含证据、完整转写片段、版本或审核状态；源文件登记继续保留。

2026-10-22 已落地机械狼通灵师单局示例，每夜7个槽位、每天10个槽位，按实际轮次重复。当前使用 `game_details`、`game_seats`、`game_staff`、`game_event_records` 等业务表，具体结构见 [对局数据库与版型模板](../../04_对局档案与数据库.md)。此前的候选、版本及审核表保留为早期试验记录。
