# 赛季数据全流程

更新：2026-10-28。采集、核实、入库、复核、发布与验收统一在本页执行；原02与15合并，字段证据按02规范查对应条目。

1. **第一步：采集原件到本机。** B站中文字幕优先，缺中文轨才取音频；微博采赛季日期窗口内官方账号全部可见发布。
2. **第二步：核实人物与身份。** 读照片名牌确定当天嘉宾，结合本局白天发言图片、开场介绍、连续复盘和已有文字，分别确认座位、姓名、真实底牌；缺少文字时才转写音频。
3. **第三步：核实日夜流程与票型。** 复用已核身份，结合本局文字、画面和复盘，记录各日夜动作、死亡/离场、警徽和每个实际票轮。
4. **第四步：用户复核悍跳与成功结果。** 按日期逐局提供12席名单、身份与原图，由用户选择悍跳人、是否成功并填写备注，再据已确认结果汇总。
5. **第五步：核对后写入数据库。** 固定本次已核结果和写入范围，复用对应赛季的来源登记与事务导入，核对回执；悍跳随对应网站对局版本发布。
6. **第六步：局部复核与意见核对。** 自己指定AI复核范围，或逐条核对他人意见；只看所提对局、字段和证据区域，因具体冲突才沿直接依赖扩大，结论足够即收尾。
7. **第七步：发布所有保留季及新季照片。** 按本次授权发布完整活动集，同步悍跳和必要照片。
8. **第八步：验收与续跑。** 核源、API与页面，记录回执、已知缺口和下次入口。

已有S22/S23及S21的已核结论直接复用，既有未知与未决项按原状态保留。以下命令用于新增缺口，参数示例不是重新采集、转写或复核已完成资料的要求。入库按第五步执行，统计与网站发布按第七、八步及本次明确范围处理，具体事实判断遵循[字段证据规范](02_字段证据与交叉复核规范.md)。

## 第一步：采集原始资料

更新：2026-10-28。用户在自己的电脑运行现有脚本，资料直接写入项目目录。本步只取原件，不启动转写、排班提取、人名识别、事实推断、数据库登记或网站发布。

### 范围与规则

| 来源 | 输入 | 采集规则 | 输出 |
| --- | --- | --- | --- |
| B站 | 官方合集及种子BV；单条补采可给BV和分P | 先取可下载的中文字幕；取得中文轨就跳过音频；本次字幕查询成功但无可访问中文轨时，只取独立音频 | 元数据、字幕JSON或音频、来源manifest |
| 微博 | 官方UID `7525583841`、赛季发帖起止日期 | 采日期窗口内官方账号全部可见发布，不按关键词、是否排班或正文提及哪一季过滤 | 帖子JSON、完整长文、配图、必要详情和分页原件、manifest |

“中文字幕”包括平台提供的中文AI字幕轨；画面内压制字幕不在本步做OCR。字幕请求失败、中文轨下载失败、字幕内容格式错误或明确要求登录时，应报错停止，不能解释成“没有字幕”后自动下载音频。平台正常返回但无可访问中文轨，只表示本次访问结果，不声称视频绝对没有字幕。

微博日期按发帖北京时间判断，起止日都包含；不是从正文猜比赛日期。合集媒体数、微博数不等于正式对局数。已有S21/S22/S23原件继续复用，示例不是重采指令。

赛季来源使用 `config/seasons.json` 中现有的 `collection_id`、`seed_bvid`；新季登记自己的来源，不借用别季合集。采集不要求先建立正式规则或启动数据库。

以下S21仅示范参数。整季有现成计划时直接run；需要获取或更新合集清单时才执行plan：

```powershell

.\.venv\Scripts\python.exe scripts/collect_season.py status --season S21
```

每条先查中文轨，有可用字幕就保存字幕；没有中文轨才取音频。顺序执行，错误停止，用户处理登录或网络问题后重跑同一命令；已有合格音轨按现有哈希复用，不自动重试、不做并发调度。

单条补采明确分P：

```powershell
.\.venv\Scripts\python.exe scripts/collect_bilibili_audio.py BV1tj8p6REqy --page 1 --subtitles-first --expected-owner 19106800 --auth cookies --cookies-file .secrets/bilibili.cookies.txt
```

不使用登录态时改为 `--auth none` 并去掉 `--cookies-file`。已有旧音频继续保留；“字幕优先”控制这次是否下载音频，不删除历史文件。旧的显式 `--audio` 仍供明确需要音频的后续任务使用，不是本步的默认采集方式。

也可用现有调度入口：`workflow.py run --season S21 --stage collect`。现在collect只执行必要的plan和run，不再串联数据库检查、字幕版本择优或音频全量审计。

## 第二步：核实当天嘉宾与每局座位、姓名、真实底牌

### 确定当天出场嘉宾

先从已采微博中定位目标比赛日的官方阵容公告，读取照片上的可见姓名牌，结合官方正文核对姓名、别名和节目职责。保留原图、原帖和比赛日期；发帖日期与比赛日期分开。照片没有可读名牌时保留待核，不凭人脸认姓名，也不把正文名单顺序与图片顺序一一配对。

可先导出本机微博的阅读与排班候选；该命令解析正文，不识读图片：

```powershell
.\.venv\Scripts\python.exe scripts/export_weibo_schedule.py "本机归档目录/manifest.json" --output "本机排班输出目录"
```

已有同一原图的确认记录，按原图SHA复用，并保留这次原帖引用；同名但不同照片仍需自己的来源依据。选手、解说、法官和其他嘉宾分开。公告安排是当天名单的线索，实际缺席、替补和换座以本局现场证据为准。

本段产物是当天嘉宾名单、规范姓名/别名及照片来源。它不直接产生座位号或底牌。

### 先复用文字与已采画面

先查本局平台中文字幕、既有完整转写、已确认的文字修订及白天发言/结算截图；有可用文字就直接定位，不重新跑ASR。复用修订稿时保留模型原稿与修改依据，不把轻校对稿冒充逐字听核稿。

复盘可以在文件中段；按明确开场、连续身份名单和收尾定位，不固定截最后一分钟。先定位与本步骤有关的姓名、座位和身份，不要求先完成全场逐人发言归属。

### 缺少文字时转写音频

只有本局没有可用字幕或现有转写，才对已有音轨运行Paraformer。若仅部分文字有疑点，先复听对应片段；确实需要音频但第一步只取到字幕时，再使用采集器已有的显式 `--audio` 补取。

主采集环境为Python 3.12的 `.venv`；现有ASR使用Python 3.9的 `.venv-funasr39` 与[既有依赖清单](../requirements/funasr.txt)。复用本机模型及CUDA环境；配置和恢复说明见[本地资源](06_本地资源与清理.md)，不要把两套依赖混装。

替换下面BV、赛季和实际分P路径；只给缺少文字的条目运行：

```powershell
$bv = '目标BV'
$season = '目标赛季'
$audio = "data/raw/bilibili/$bv/p01/audio.m4a"
$manifest = "data/raw/bilibili/$bv/p01/manifest.json"
$out = "data/transcripts/$season/${bv}_p01_funasr"
.\.venv-funasr39\Scripts\python.exe scripts/transcribe_funasr.py $audio --manifest $manifest --no-speakers --out $out
```

`--no-speakers` 使用现有开关关闭匿名声纹。输出包括 `transcript.json`、SRT、阅读TXT、配置、VAD计划和 `raw/chunk_*.json`。同一音频与配置可复用已完成分块；换音频、热词、设备或配置时使用新目录。CUDA不可用会明确失败；需要CPU时显式指定 `--device cpu`，不在续跑中自动换设备。

Paraformer模型未在本机缓存时，现有脚本会按原模型ID获取；先确认环境和模型位置。只有缺文字才进入这一段，已有文字无需加载模型。

### 按需补取白天发言和复盘画面

先看已有截图；仅对缺少的姓名牌、座位牌或真实身份揭晓位置补图。根据字幕/转写选择时间点，保留前后必要画面，不逐秒扫完整视频。

通用单条截图入口已接通现有Cookie参数，读取已采manifest中的BV/CID：

```powershell
$bv = '目标BV'
$season = '目标赛季'
$media = Get-Content -LiteralPath "data/raw/bilibili/$bv/p01/manifest.json" -Raw | ConvertFrom-Json
.\.venv\Scripts\python.exe scripts/capture_bilibili_frame.py $media.bvid $media.cid --times "600,1200" --out "data/extractions/$season/frames/$bv" --auth cookies --cookies-file .secrets/bilibili.cookies.txt
```

截图需要现有PyAV媒体依赖，见[依赖分组](../requirements/README.md)。PNG保留原尺寸，名牌裁图另存。通用截图文件名中的秒数是请求定位点，不能冒充实际帧PTS；已有 `capture.json` 记录了实际帧时间的，继续保留该记录。OCR只提供候选，照片与侧栏都要实际查看。

### 核实每局座位、姓名和底牌

| 字段 | 可以采用的证据 | 必须分清的含义 |
| --- | --- | --- |
| 座位—姓名 | 本局编号姓名牌、开场自我介绍、法官点名及对应发言画面，结合当天照片名牌 | 微博照片编号、正文顺序、声纹编号都不是座位号；换人换座按本局更新 |
| 真实底牌 `role` | 法官连续终局身份复盘、明确真实身份揭晓；局中真实翻牌作补充 | 黄色自称栏、玩家跳身份、解说推测、胜方OCR及“奇幻视角”身份伪标不能直接作底牌 |
| 未明确的字段 | 保留空值/未知和具体缺口，按原记录格式表达 | 不因姓名或角色没读出来而补平民，不强行凑齐人数或角色配置 |

姓名与底牌分字段引用证据：同一张图的名牌可能可用，而身份栏不可用。角色词须连续读取，例如“通灵师一号、女巫十号、猎人七号、守卫五号”，不能按字幕断行错配。仅在实际版型与其余底牌均已确认、剩余解唯一时作明确标注的推导。

跨局复用座位必须有同日同阵容且未换座的依据；不能只因当天是同一批嘉宾就复制整张座位表。物理底牌与学习形态、临时技能、个人胜利阵营分开，后者不是本步骤补齐的前提。

本段产物是：当天嘉宾来源记录；逐局 `seat/name/role` 及各自的原图/原文、BV/CID/P、原媒体时间和已有SHA关联；尚未确定的字段及原因。沿用现有文件格式，不另建通用状态体系。

### 模糊字词的复听与可选复核

先回听原音频，重点核对数字、否定、姓名和连续角色名单。按原时间轴裁取明确窗口：

```powershell
.\.venv-funasr39\Scripts\python.exe scripts/extract_audio_window.py "原音轨路径" --start-ms 2034000 --end-ms 2060000 --out ".cache/review/目标BV_2034000_2060000.wav"
```

WAV旁的 `.source.json` 保存原时间范围与来源；引用局部稿时加回该偏移。需要第二份机器稿时，再按需用 `review_asr_clip.py` 处理不超过30秒的片段，输出到新的目录。模型一致不等于听核正确，Nano不是默认必跑环节，也不覆盖主转写。

## 第三步：核实日夜流程与票型

### 固定本局输入与范围

使用第二步已核的座位、规范姓名和物理底牌，读取同一BV/CID/P的完整字幕或转写、白天程序/投票画面及连续法官复盘；按需补图或复听沿用第二步入口。先确认本局实际版型与当季规则，再判断技能结算、票权和推导；标题Day、节目期数不是局内日次。

本步记录真实发生的日夜流程、警徽和逐人票型；悍跳判定、理论绑票、胜负积分统计、正式入库和发布留待相应后续范围。终局发生时点可以作为停止后续常规流程的边界，不为补齐格式继续造票轮。

### 先恢复日夜主线

先从连续复盘建立明确动作骨架，再回到局中程序与画面逐项核对。无复盘时仍可保存局中直接证明的部分，未证明的夜间细节继续未知。

| 本局阶段 | 现有内部定位示例 | 核对重点 |
| --- | --- | --- |
| 开局夜晚 | `night, round=1` | 本局角色的首夜实际动作 |
| 第1天白天 | `day, round=1` | 初次上警/警下、退水、警徽、死亡公布、投票与离场 |
| 第1天夜晚 | `night, round=2` | 白天结束后的下一夜，不挪回第1天白天 |
| 第2天白天 | `day, round=2` | 下一白天的程序与独立票轮 |

上表是现有S21/S22/S23数据的夜次与展示日序映射，保留原有编号。逐项记录行为主体、动作、原目标、实际影响对象及结果；交换、反弹或临时技能按本季证据分开表达，不把物理底牌改成学习形态。

`performed` 表示已执行；`pass` 是明确空过；`unknown` 是未核清；`forbidden` 是禁止；`not_applicable` 是不适用。未执行状态不填写成功目标或实际命中对象；未知动作不补成空过、平安夜或未死亡。

复盘的时间戳定位的是“这句话在原视频何处”，不是动作发生时间，也不能按复盘列举先后推定实际睁眼顺序。实际夜死、次日公布死亡、技能触发和真正离场分别核对；投票后才开枪造成的死亡，不反过来取消那次投票资格。

### 按实际程序拆分每个票轮

先确认该轮确实举行，再记录所属白天、警长票或放逐票、首轮/实际PK/技能重投、候选池、已证明的有票权名单、逐人投向/弃票和最终结果。首次上警与原始警下名单、退水后的候选、次日延期竞选分别保留。

- 同一天的首轮、PK和技能重投分别保存，不能用最后一轮覆盖前一轮；“归票甲乙PK”一句话不证明后来实际重投。
- 两轮都平票，保留两轮票型和“无人放逐”的结果，不能记成整天没有投票。
- 逐条核对“投票人→目标”；合并报票按原句中的完整座位组读取，数字和断行含混时回图或回听，不按总票数猜分配。
- **未知投向不等于弃票。** S21现有格式中，目标为空的三项式票行会被记作 `abstained`；未知投向应缺省该票项并记录缺口，不能写成一张空目标票。
- 默认弃票仅在实际票轮、完整资格集合和适用约定均已确认时使用，并保留资格依据及“默认”标记；票权不明、整轮未找到时不补造弃票或投票轮。
- 依据投票发生时的现场程序与适用规则确定资格；首夜死亡可能在警徽竞选后公布，不能只按复盘夜死名单剥夺此前竞选票权。

延期竞选等规则分季适用：既有S22约定是首日自爆中断未完成竞选才延至次日，次日再次自爆则流徽；原始警下集合与已知离场者共同确定续投资格。不得直接推广到未核实的其他赛季。S23特定绑票分析的警长半票属于理论票力，不替代逐人实际票型。

### 局中、复盘与后续结果互证

按实际日夜顺序核行动资格、死亡/离场、警徽和投票；再用后续明确发言、票轮、技能及终局复盘反查。角色词、否定、目标和“第几天”有歧义时回到连续上下文。

同一动作被局中播报和赛后复盘重复描述，应给同一事实保留多份依据，不新增第二次动作或票轮。相同座位在不同轮重复行动则是不同事件，不能按目标或相似文本全局去重。保留S21有明确原文的“吞毒自爆”等实际程序，不能重复算死亡或因此恢复票权。

终局推断若与后续实际票/行动冲突，保留原件并复核终局判断；不静默删除后续证据。仅在已确认当季规则、输入和唯一结算时推导，推断与直接原话分开，多解继续标明缺口。

### 最小输出和现有入口

沿用该季已有事件/票型格式，保存：每个日夜的动作与结果、死亡及离场依据、各票轮及资格/候选/逐人选择、警徽变化、对应文字段号/原时点/画面引用，以及明确缺口。原话、画面观察、规则推导与用户确认保持区别，不另建通用状态机或第二套审计台账。

| 工具 | 使用范围与实际产物 |
| --- | --- |
| `s21_phase_review.py pack/build` | S21专用。已有文字索引、身份JSON、复盘候选时生成阅读包；人工核实并填写 `phase_specs` 后，生成本机 `phase.reviewed.json` |
| `audit_s21_phases.py` | 校验S21文字/结构与时序，输出既有警告报告；校验错误返回非零，警告和缺口仍需判断，不代表自动核实全部事实 |
| `import_s21_phases.py` | 还要求独立的 `phase_primary_audit.json` 批准绑定spec SHA；默认生成本机结果/缺口报告，只有显式 `--import-db` 才写DB；不是本步必跑 |
| `voting_records.py` | S22旧批处理专用，依赖已整理dossier、全文及本季补正；会重建逐局票型和审计，非通用新赛季入口 |
| `s23_phase_review.py` 与S23构建器 | 读取已有S23复核文件并补阶段缺口，构建器还含其他产物；不能替代逐局读图/读文，也不作为本步默认整链 |

S21已有配套输入时，只针对需要新增核实的真实BV使用：

```powershell
$bv = '替换为S21索引中的目标BV'
.\.venv\Scripts\python.exe scripts/s21_phase_review.py pack --bvid $bv
# 实际读完复盘与局中证据，按已有格式填写 phase_specs/<BV>.json 后：
.\.venv\Scripts\python.exe scripts/s21_phase_review.py build --bvid $bv
.\.venv\Scripts\python.exe scripts/audit_s21_phases.py --bvid $bv --summary
```

`pack` 只是定位阅读范围；未找到复盘锚点时的末段窗口也只是候选，不能当作已经找到复盘。`build` 要求实际阅读的复盘与局中区间都存在；缺一类证据时不虚填跨度满足程序。审计的 `--bvid` 报告只覆盖所选录像，不能称为全季验收；它不生成独立主审批准文件。

当前S21构建器的事件/票项入口是文字段索引。只有画面证明、文字未直接播报的票，按现有复核旁证保存画面与结论，不能硬挂一句无关字幕来冒充证据；该构建器不能单独替代这种画面核实。新赛季按现有本机证据逐项记录，不只改旧脚本季名或日期就宣称自动恢复全部流程。

### 第三步的减法结论与停止条件

| 机制 | 本次处理与依据 |
| --- | --- |
| 每条证据重复计算同一选定转写SHA | 改为每局build计算一次并复用；原先仅重复填元数据，没有额外比较，输出证据哈希保持不变 |
| 每个白天事件重复生成当夜中毒集合 | 移至该日夜循环中计算一次，吞毒自爆等判断语义不变 |
| 未执行动作只检查原目标 | 同一已有约束同时覆盖实际目标；不能在 `unknown/pass/forbidden/not_applicable` 下保存成功命中 |
| 审计捕获所有异常却返回成功 | 只处理预期的文件/字段校验错误并以非零退出；内部意外错误暴露，不新增重试或fallback |
| 来源SHA、spec批准绑定、轮内重复投票与资格检查 | 保留；分别防止错源、旧批准套用新spec、同轮重复选票和不合法票权 |
| S22/S23因果结算回退、延期竞选与季别规则分支 | 保留已有真实用途及关键测试，不泛化到其他季，也不以理论结果改写原票 |
| DB事务、锁、读回和无关表保护 | 留在显式入库路径，第三步的本机核实不触发 |

日夜骨架和实际票轮均可回源，已知结果相互一致，未定项有具体缺口；完成相关回归后收尾。不因缺原文就凭空补夜晚、行动、弃票或下一轮，也不为本轮再启动全仓一致性扫描。

## 第四步：识别悍跳与计算成功率

### 默认由用户填写，助手准备名单和证据

2026-10-28起，悍跳及是否成功由用户自行复核，后续赛季也沿用此方式。助手按日期分组、逐局列出已核12席的座位、姓名、物理底牌，附对应身份画面／结算截图、复盘原文和原视频入口。名单和证据放在填写区前面。

每条填写只有三列：**悍跳人、是否悍跳成功、备注**。候选是该局全部12人，包含混血儿，不能先用物理狼人或个人阵营过滤。支持同局多人；狼混、发生日、所跳身份、特殊情况等由用户在备注补充。未填写、待定、明确无人悍跳和已复核分别保存，不把留空当否定。助手不自动判断、不预填结论，不继续逐局识别发言；用户主动要求核某条时才围绕指定证据协助。

S21当前[人工复核页](../data/exports/S21_悍跳人工复核.html)覆盖42个日期、122条保留媒体。页面自动保存当前浏览器草稿，可导出／导入JSON；导出后保留BV/CID/P、名单、来源SHA与用户填写。旧AI草稿位于[未采用归档](../data/archive/S21_bluff_ai_draft_20261028/README.md)，不作预填或统计输入。

S23重新人工复核从[人工复核页](../data/exports/S23_悍跳人工复核.html)进入，覆盖23个日期、75局正赛、900席。名单、日期和局次取当前正式档案，复用已有截图与已核复盘窗口；采用同一空白表和导入导出格式，草稿按赛季及来源指纹隔离。旧S23推断、用户反馈及已确认边界继续保留，不预填到新表。

输入是同一局的已核座位/姓名/物理底牌、个人有效胜利阵营、第三步的真实日次、警长竞选与最终放逐，以及本人发言的原文、画面或原声定位。姓名继续沿用既有人物映射。前面已有证据直接引用，疑点才按第二步补图或复听，不重新做整局ASR。

现有网站统计代码的旧口径要求物理狼人、个人狼人胜利阵营、本人公开自称预言家或通灵师；这不是人工页面的候选限制。用户填写的混血儿／狼混记录完整保存，后续应用用户结论时再核对应统计适配，不能被旧物理狼人筛选静默丢弃。本人自称、引用或假设仍须结合前后句理解。

从第一天警上、实际PK、警下发言连续核至真正入夜或自爆中断；竞选延期到次日及更晚起跳另看对应话轮，记录实际发生日。画面摘要中的验人、身份与警徽流用于交叉核对本人发言，缺少摘要不能据此判“没悍跳”。晚期复盘可以证明早先的起跳，不能把后日自称倒填首日。

历史 `assessment` 的 `yes/no/uncertain` 仅保留原有来源与确认级别，不用来替用户填写新表。用户导出的每条选择保留座位、成功选项与原备注，不自动补身份、发生日或阵营。统计应用时同人同局去重，尚未确定的结果继续单列。

遗言等边界按已确认作用域处理：S23 2026-10-09第三局10号遗言起跳已由用户确认不计入，该局6号悍跳保留，见[最新交付记录](../data/reports/S23/S23_悍跳本次交付_20261026.json)。既有定案直接复用；其他未确认边界保留独立宣称和具体疑问，不把这一局扩成全赛季新规则。助手推断、用户确认和用户仍不确定分别记录；dot的建议须由用户决定是否接受。

### 悍跳成功沿用既有两项条件

先确认悍跳发生，再核成功；同一人同一局只保留一个成功结果，满足两项也只计一次。

| 情况 | 采用的结果 |
| --- | --- |
| 起跳者在起跳后通过警长竞选获得警徽 | 成功；延期竞选核实际发生日，起跳前已拿徽及警徽继承不算 |
| 首日起跳，首日最终被放逐者个人有效阵营为好人 | 成功；按狼队战术结果，不额外要求起跳者本人归票或过半好人跟票 |
| 两项适用条件均明确不满足 | 失败；首日自爆中断无放逐不能顺延为“第一轮有票的白天” |
| 所需发生日、竞选或最终放逐结果尚不明确，且没有已证明的成功条件 | 成功未知，列具体缺口；不能默认失败 |

首日放逐只看最终结果，首轮平票暂时高票、夜死、毒杀、开枪及次日放逐都不能代替；延期/后期起跳不能追溯借用此前首日放逐。整局狼人获胜、起跳者存活或他人竞选拿徽也不直接决定该人的悍跳成功。

成功判断复用第三步已核事件及票轮。正式数据缺失警徽结果时，可保留已有带定位证据的专项结果复核；补充流徽不得覆盖已明确的竞选当选。证据冲突回到对应局解决，不新增一套投票、存活或终局推断逻辑。

### 次数与成功率

按选定正式对局范围，以同一人物同一局为单位汇总：

- **悍跳次数**：`decision=yes` 的去重局数；归属不明的局不计已识别次数，单列待核。
- **成功率**：成功数 ÷（成功数 + 失败数）；成功结果未知的已识别尝试不进分母。
- **无有效分母**：显示“—”/空值，不能显示0%。同时保留待核局数及成功未知数，不能用一个百分比掩盖覆盖缺口。

例如已识别5次，其中3成功、1失败、1成功未知，另有2局悍跳归属未定：次数为5，成功率为 `3/4=75%`，并列出这3项未定。现有 `bluff_success_rate.excluded` 合计归属未定和成功未知，不能把它全部解释成“已悍跳但结果未知”。跨赛季汇总累加分子、分母，不平均各季百分比；原件条数、重复发言与非正式表演局不扩大正式样本。

S22的 `--allow-partial`、S23的 `--allow-partial-audit` 仅用于明确标注未完成范围的交付，不作为完成核实的默认开关。去掉 `--check` 会写本机网站资产和复核导出，S23还会复制已有截图及更新图片清单；第四步日常先完成逐局证据和本机判断。`website.api.publish_bluffs` 属于后续数据库发布路径，其 `--check` 也需要活动DB快照，不列为本步命令。

S21人工页构建器去掉 `--check` 仅生成上述人工复核页及[来源验收](../data/reports/S21/S21_悍跳人工复核页验收.json)。复用已有截图与阅读版全文；不改变身份、流程，不预填悍跳或成功结果。奇幻视角画面可能伪装底牌时，同时展示已核复盘更正说明和原文。当前边界是122条保留媒体，不能据此宣布122个正式对局。

S23使用 `build_manual_bluff_review.py --season S23` 生成上述新人工页及[来源验收](../data/reports/S23/S23_悍跳人工复核页验收.json)，不覆盖旧推断页，不写数据库或网站资产；用户填写后的结果按下段应用。

S23用户已于2026-10-29提交人工JSON并授权应用，详见[应用差异与回执](../data/reports/S23/S23_悍跳人工复核应用_20261029.md)。`build_manual_bluff_publication.py --manual <文件>`只校验当前来源和活动对局绑定、比较结果；加 `--prepare` 才归档原件并写本机悍跳资产和报告。检查后使用既有 `python -m website.api.publish_bluffs --season S23` 事务写入悍跳版本表。明确人工成功结果优先于自动规则；用户逐条选中的混血儿单独纳入。未填写局保留原值，原始 `reviewed` 勾选不替代用户在会话中的明确应用授权。

**人工复核定案后锁定。** 已确认的悍跳、不是悍跳、成功、失败及人工保留的待定值，除非用户明确要求修改，否则原值、备注和统计口径均不改变。技术签名缺失、证据路径迁移、规则或其他输入变化，不能自动把人工定案降级为待核、清空结果或剔除统计；发现实际冲突另行报告，由用户决定是否修订。

依赖签名用于检查程序推断与用户新提交的修订是否对应当前输入，不决定既有人工作结论是否有效。程序推断的悍跳归属与成功结果分别绑定人物、自称话轮、证据SHA、起跳阶段、警徽、首日最终放逐和有效阵营等依赖；相关输入变化时只重新核对这些未定案推断。S23已有67条人工成功/失败结果已入数据库，继续按人工值统计，无须因为缺少新签名而重新复核或重新入库。

页面的“悍跳成功结论（可选）”默认留空，可明确选择成功、失败或待定。导出反馈后，`import_bluff_feedback.py`默认预检，`--apply`只保存意见；S22由既有推断构建器、S23由人工结果构建器应用明确的成功反馈。未填写成功结果的意见不会重置已有人工结果，也不会补造确认。

新赛季可以沿用现有复核字段逐局记录，并复用统计函数的输入契约；新增角色或发布适配应有该季实际规则依据，不只替换脚本里的季名或局数。无需为本步新增识别服务、多模型投票、通用分类框架、额外状态或统计缓存。

### 第四步的减法结论与停止条件

| 机制 | 处理与依据 |
| --- | --- |
| 同一局每个狼位重复计算相同事实指纹 | 每次处理该局时计算一次并复用，指纹内容与证据绑定保持 |
| S23已有独立复核时仍先构建再丢弃旧判断 | 旧判断只在没有独立复核时构建；仍读取原文件、核BVID并保留独立遗言宣称和明确用户反馈 |
| 来源指纹、证据SHA与原文时间窗核对 | 保留；防止身份/票型变化后沿用旧判断，以及把错图、错原文绑定到结论 |
| 首轮/最终票轮、流徽/未知、首日/延期/后期与独立遗言记录 | 保留；它们实际改变成功结果或统计范围，不能合并成默认值 |
| S22/S23旧输入兼容、已复核记录和明确用户反馈优先级 | 保留现有消费者和用户定案；不增加第三套回退推断 |
| 发布事务、活动版本绑定、图片清单及公开路径限制 | 保留在相应边界；本机核实不自动触发发布 |

本次范围内每个待核狼人有可回源的结论或明确缺口；成功条件与第三步一致；次数、成功/失败、分母及排除项能相互核对。完成相关回归后收尾，不为提高覆盖率把未知改成否或失败，不重复核实已有定案。

## 第五步：核对后写入数据库

### 先固定要写什么

输入是第二至四步已核的本机结果及其来源，先指定目标赛季、对局和本次字段范围。按实际材料核对座位/底牌、真实日次、存活与行动资格、各票轮、警徽和悍跳结果；发现矛盾回到该字段的原件处理，缺失继续未知。完成本次核对即可进入相应导入，不再加一轮全仓审计。新赛季需要适配时先验证一局普通样板和一局实际特殊情况，已有定案不因此重做。

正式 `dossier.json`、`voting.json` 等沿用各季现有格式；原始字幕、音频、图片、逐字稿和判断依据继续保存在磁盘及来源登记中。不要把复核全文、临时意见或成功率缓存塞进座位和日夜事件表。批量格式支持的未知保存为空/unknown，严格 `--final` 所需信息缺失则保留为未定稿，不能自动补平民、空过、弃票或胜方。

### 使用现有表与入口

| 数据 | 写入位置与现有方式 |
| --- | --- |
| 原件与来源关联 | 业务库 `sources/artifacts`，保留平台外键、原路径、已有SHA及小型证据快照；登记原件不等于核实对局 |
| S21专项核实与正式对局 | 原 `extraction_runs` 及 `reviewed_identity_seats/reviewed_phase_records` 保留证据；`import_s21_formal.py` 将已核记录转换为正式dossier、票型和终局，再写现有业务表 |
| 已适配的正式对局 | 业务库默认 `jcms` 下的 `people/person_aliases`、`games/game_details/game_seats/game_staff/game_rounds` 及事件、目标和效果表；原件关联在 `game_files` |
| 完整逐日票型 | 同一业务库的 `game_ballots/game_ballot_choices/game_voting_days/game_sheriff_registrations`；与事件槽中票型分别核对，不能只导dossier就声称所有票型已同步 |
| 悍跳明细及版本 | 网站库默认 `masters_web` 的 `bluff_review_publications/bluff_review_items/active_bluff_reviews`，绑定活动对局release；成功率复用第四步公式从已绑定明细计算 |

业务入库和网站发布各自沿用现有事务。写业务库不会自动刷新网站，第四步本机悍跳JSON也不会自动成为网站活动记录。网站须先发布匹配的正式对局版本，再发布该季悍跳；网站发布入口留在后续步骤，本步不运行整条 `publish` 链。

### 先登记来源，支持只有中文字幕的原件

已登记的同一来源直接复用，不重复采集。已有音轨或已下载的有效中文字幕，都可离线登记原件：

```powershell
$bv = '需要补登记的真实BV'
.\.venv\Scripts\python.exe scripts/collect_official_audio.py $bv --page 1 --register-existing
```

该命令校验本机manifest及官方UID/BV/CID/P，并写原始库。清单含音轨时仍校验字节数/SHA/时长与解码；清单无音轨时校验已下载中文轨及字幕段落，不登记或下载音频。不访问B站、不开始ASR、不创建正式对局。已有登记时不用再跑。首次建库或确有待执行迁移时才用 `database.py migrate`，不是每次入库都执行的步骤。

正式对局的主来源是本局录像对应的 `source`，音频、字幕和转写只是不同来源文件。`game_records` 和S22定稿入口均接受其中任一种，同一录像后续补上音频不会换掉对局来源；已声明但损坏的音轨仍报错，不借字幕掩盖错误。字幕-only不要求安装或运行ASR模型。

旧 `register_season_transcripts.py` 继续服务已绑定音轨SHA和旧审计CSV的历史转写登记；新字幕原件直接使用上述登记入口，无需先伪造旧格式。S23固定75局导入仍读取其原有音轨快照；这条历史适配不限制通用或S21字幕正式入库。

### 按当前赛季选择最少命令

| 当前范围 | 可复用入口及写入边界 |
| --- | --- |
| S21已核身份 | `import_s21_identities.py` 默认生成本机结果；加 `--import-db` 才写已复核身份层，要求现有迁移已就绪 |
| S21已核日夜/票型 | `import_s21_phases.py` 还要求现有独立主审文件 `phase_primary_audit.json` 与spec SHA匹配；默认生成本机结果/缺口，加 `--import-db` 才迁移并写专项payload |
| S22单局修订 | `workflow --stage import --bvid ...` 备份后调用 `batch_s22.py import-edits`，按本局slug替换结构化事实并写收据；当前不串联完整 `voting.json` 导入 |
| S22新建已核草稿 | `formal_entry.py check/import <file> --final`；复用已有来源及实际版型，`init`仅新建未存在的草稿。`import`会重校验，单独check是预览，不必机械重复 |
| S23单局修订 | `workflow --stage import --bvid ...` 备份、按当前有效记录生成该局候选、prepare正式JSON、单事务写一次；无变化不重写，继续核对来源、回执与跨季保护 |

S22完整票型如有修订，沿用 `voting_records.import_voting(facts, conn=...)`；该函数接受已有完整本局票型，调用时与本局事实共享事务，避免一半更新。现有 `voting_records.py --import-db` 是S22整季重建/导入入口，不列为单局修订的默认补救命令。这里描述真实入口限制，不额外创建自动重建管线。

以下是命令预览示例，只有目标及来源已明确、确需修改对应业务库时才执行 `run`：

```powershell

.\.venv\Scripts\python.exe scripts/workflow.py run --season S21 --stage import --bvid $bv

.\.venv\Scripts\python.exe scripts/workflow.py plan --season S23 --stage import
# 需要写入该快照时
.\.venv\Scripts\python.exe scripts/workflow.py run --season S23 --stage import

# S23：日常单局修订；同一正式对局路径内只准备、写入所选BV
```

按本次目标选择对应示例。S21旧专项入口保留原有行为；需要时先备份，再运行对应 `--import-db`，其默认命令仍会生成本机报告。新正式适配器的默认 `--check` 则只在内存核对；已核字段进入正式结构不代表所有字段已补齐、计分总局数已确认或网站已发布。S21未知角色配置和叫醒顺序不套用其他季；不能压入固定事件槽的细节及原始phase记录另存旁证，不默默丢弃。通用 `game_records.py` 默认直接写库，`--check-only` 才仅校验，日常优先采用上表对应的明确入口。

### 必要保障与收尾

写库前沿用现有 `backup_database.py` 生成整库dump和保留季基线。它保存完整数据库，媒体文件仍在本机原目录；`pg_restore --list` 成功只证明备份目录可读，`restore_verified:false` 不表示完成实际恢复。它依赖已初始化的网站schema和现有保留季正式资料；新空库不能假装拥有这些基线。

保持每局/每批事务、来源及slug归属、必要锁、唯一键和外键。S23完整验收在同一外层事务内重复导入并比较内容指纹；指定BV时按当前单局输入、正式文件与数据库回执识别变化，只写变更局一次，并核对跨季保护。日期或局次改变正式目录时需完整重建范围。专项导入核对读回payload和无关表。导入失败回滚事务；失败后以数据库状态和回执核对，不盲目重试或自动换源。

| 机制 | 减法结论与依据 |
| --- | --- |
| S23日常修订与完整验收 | 指定BV时只生成、准备和导入该局；不指定BV时保留完整双遍验收。导入边界重新检查当前有效候选、正式文件和DB条件；独立check/check-db按具体需要调用 |
| 原件/规则/迁移/收据SHA与内容指纹 | 保留；分别约束错源、已执行迁移变化、候选版本混用及同数量内容被改动 |
| 已导入文件再次校验 | 仅在独立命令、人工编辑或真正写库边界复验，避免在同一可信调用链新加检查层；不绕开现有导入校验 |
| 幂等、事务、跨季与模板保护 | 保留；不得用删测试或忽略冲突换取较短导入代码 |
| 未知缺省、自动补采音频、失败自动重试、第二套导入框架 | 不增加；按现有字段语义报告具体缺口，已支持的字幕-only路径直接登记和导入，不增加音频依赖 |

完成条件：本次选定输入与写入范围明确，必要来源已登记，导入回执与数据库实际内容一致，重复导入不多增记录，失败回滚和无关数据保护经相关测试验证。尚未入库、未适配、未发布各自如实记录。没有指定新赛季/对局资料时，本步只整理入口与验证，不擅自重导已完成的历史数据。

## 第六步：局部复核与意见核对

日夜、技能和票型复核先读本局`rule_derivations.json`的`review_tasks`、`vote_review_tasks`、`issues`及其存活/资源前提。已由共用规则排除的死者、耗尽药剂、未解锁技能和未发生阶段不用重复查证据；实际操作、未知目标及规则冲突才回原件。修改基础事实后按局重新生成推导，具体命令与跨季规则见[通用规则推导](07_通用规则推导.md)。

### 两个入口，共用一条短流程

本步用于独立检查已有判断，也可在第五步写库前使用。第二至四步负责建立事实，本步按用户指定范围复核这些事实；修订后再回相应步骤更新。本次未提到的对局、字段、画面区域保持原状。

| 入口 | 开始时要明确什么 | 最先做什么 |
| --- | --- | --- |
| 自己让AI复核 | 哪一局、哪几个字段或区域、要回答的问题；只给局号时可从已有索引自行定位BV | 读取这几个字段的当前值与已有证据 |
| 核对别人意见 | 原意见及其对局、字段、建议值或理由，沿用对方编号 | 先比较意见和当前值，已修正项直接注明；其余回原件核对 |

范围用一句话写清即可，不另填任务单。给定整局才覆盖整局；给定几张图、几个座位或一轮投票，就只核这些对象。BV、局次或图中对象确实无法定位时，只问缺的定位信息；能从现有索引找到的自行查找。

### 五个动作及结束条件

| 动作 | 具体做法 | 何时结束 |
| --- | --- | --- |
| 1. 锁定范围 | 写明本轮对局、问题/字段、原意见编号和已给证据位置；对照当前文件，确认旧意见是否已处理 | 每条意见能对应一个目标；缺定位的单列 |
| 2. 读最小证据 | 先用已有核实结果和来源定位，再读对应原文/原图；同一BV、同一窗口的多条意见合并读一次 | 足以辨别本次字段含义与来源归属 |
| 3. 给出判断 | 逐条给“应修改”“维持原值”或“暂无法判定”，附证据位置及一句理由 | 每条所提问题有结论或具体缺口 |
| 4. 只追实际影响 | 当前值不变即结束；值要变时，只核它影响的存活、票权、终局或统计，见下表 | 后续结果未变，或已定位确受影响的下一项；没有新冲突就停止向外扩 |
| 5. 简短交付 | 单条用几句话，多条沿原编号列表；有修订时列旧值→建议值及受影响项 | 覆盖本轮问题，注明未检查范围与是否写入；不再启动新一轮全仓检查 |

只要求复核时，结论作为建议交给用户决定。用户已明确要求“复核并修正”或已接受具体建议时，在该授权范围内直接处理，不重复请求确认。收到dot或其他AI的意见本身不等于用户接受。

### 原文、图片、音频分别怎样省时

- **原文**：从所指时间、段号或原句读起，补足说话人交接、否定词和结果公布所需上下文；含义仍不清才向相邻话轮扩展。只核一票就定位那一票及所属票轮，不通读整局逐字稿。
- **图片**：先用原图确认录像、日号、票轮和图例，再读指定名牌、身份栏或票型区域。只核姓名就读该名牌；其他座位和身份栏不顺手重新识别。裁图缺少必要图例时补看原图对应边缘，不为此全季找图。
- **音频/补图**：数字、姓名、话轮或图层出现实质歧义时，才复听对应片段或补相邻截图。沿用第二步的裁剪与定位工具；已有可用文字时不重跑全文ASR，不默认多模型复识别。
- **外部意见**：核对对方实际引用的版本和证据，不把“另一AI也这样说”当独立事实依据。对方没给定位时先查目标字段已有证据；能明确判断便收尾，不反向证明整局其余内容都正确。

复核只读必要资料，引用已有来源及哈希；不为一次回复新建任务队列、全仓指纹或重复证据包。多局互不依赖时可按局分组并行，同一局共享已读上下文；不强制每条意见再过第二个AI。

### 什么时候必须扩大，扩大到哪里

只有发现具体矛盾，或已决定改变的值确实影响另一结论时，才沿这条依赖继续。扩到新对象时简述原因；普通小改动不重开其他已定案。

| 本次变化 | 只检查这些直接影响 | 可以停止的位置 |
| --- | --- | --- |
| 姓名或别名 | 本局座位对应、人物关联；同一映射确被其他局引用时核对应引用 | 人物归属和受影响统计关联一致；不重看夜间行动 |
| 某一张选票 | 该轮投票资格、计票与最终结果 | 结果没变即停；结果变了才追该次离场及后续资格 |
| 夜死、出局或日次 | 对应公布时点，以及该座位后续确受影响的发言、行动和票权 | 状态重新一致且后续结果不再变化 |
| 警徽归属 | 对应竞选/移交、受影响票轮的实际票重，以及该人的悍跳成功条件 | 票轮结果和该条成功判断一致 |
| 一条悍跳意见 | 该人的物理底牌、自称话轮/发生日，以及已核拿徽或首日最终放逐 | 该人该局的次数、成功与分母贡献确定；不复核其余狼人全部发言 |
| 证据错源或版本变化 | 本次引用的正确BV/CID/P、原文/图及真正引用了该证据的结论 | 已找到正确来源或列出明确缺口；不凭同名文件扩大为全季复查 |

受影响的统计可以按现有代码重算；重算汇总不等于重新人工核实所有历史局。若没有直接影响其余结论，就不把其余未知字段列为本轮待办。

### 可以直接交给AI的两种说法

自主复核：

> 只复核【赛季/日期局次/BV】的【座位/日夜/票轮/字段】，证据在【原文时间/图片及区域】。先对照当前值，必要时读相邻上下文；每项给结论、定位和理由。只有具体冲突才追直接依赖，其他内容不查。本次只给建议。

核对外部意见：

> 请核对以下意见【粘贴原意见及编号】。只处理意见提到的局和字段，先排除已修正项，再回原件判断。逐条给应修改、维持原值或证据不足；说明改值的直接影响。范围内问题有结论或明确缺口后收尾，由我决定是否接受。

如已决定让AI实施，把末句换成“对已证实的问题直接按本次范围修正，并运行与修订相关的验证”。无需每次附整季代码、完整媒体和历史交付包；优先提供目标文件、必要片段与当前值，能定位后再按缺口补材料。

### 现有脚本的范围与副作用

日常事实复核仍由AI或人查看指定证据。S23现在有单局机械检查入口：审计、预览、候选生成和导入准备均复用 `s23_effective_game.py`，按原顺序应用主审补丁、姓名/局次覆盖和逐日补正。只在姓名缺失且需要同日阵容复用时加载直接关联局的记录并核对来源SHA，不解析关联局全文。导入拒绝与当前有效记录不一致的旧候选。

```powershell
# 只读检查并输出差异到终端；--field可重复，字段路径的座位/轮次使用业务编号
.\.venv\Scripts\python.exe scripts/check_s23_game.py --bvid $bv --checks structure evidence --field 'seats[7].name'
# 默认检查structure/rules/evidence；workflow run另存该BV局部报告，不覆盖全季验收
.\.venv\Scripts\python.exe scripts/workflow.py plan --season S23 --stage review --bvid $bv
.\.venv\Scripts\python.exe scripts/workflow.py run --season S23 --stage review --bvid $bv
# 已接受补正后，只重建该局候选；不重写全季页面、进度和快照
.\.venv\Scripts\python.exe scripts/build_s23_review.py --bvid $bv --require-complete
```

报告包含当前有效数据、正式值→候选值差异、关联证据、直接影响、版本与计时。`--field`限制差异及原文旁证读取，结构/规则推演可在本局重算；未找到对应旁证会明确列缺口。通过程序检查不等于事实已核实。完整结构校验/生成仍需显式 `--full-season`，不能与 `--bvid` 混用。

```powershell
# 只有确需整季结构校验/生成时才预览；plan不执行这些命令
.\.venv\Scripts\python.exe scripts/workflow.py plan --season S23 --stage review --full-season
```

把 `plan` 改为 `run` 会实际执行旧整季链：S22写整季审计报告，S23还会生成全季候选与复核页面。它们属于机械检查/生成，不代表逐字段人工复核完成。普通一条意见不调用这条链。

S21的 `pack/build --bvid` 也会写本机材料，`audit_s21_phases --bvid` 会改写审计报告；S22的 `s22_text_review.py apply` 会整批应用并写库；`import_bluff_feedback.py --apply` 会保存意见。这些都不能冒充只读取证。需要应用已接受意见时，再按对应入口的真实范围操作。

入库事务、来源绑定和发布快照的完整性校验继续保留。局部复核不等于能跳过写入边界；若更新版本必须重建某季快照，那只是必要生成，不要求再人工复核该季所有事实，也不能声称未查看的部分本轮已通过。

### 停止条件

本轮点名的问题逐条有结论或可定位的缺口，已触发的直接依赖得到核对，即结束。回复可注明“本轮只核了X，未检查Y；未改库/已按授权修正”。资料不足保留未知；与当前值一致、旧意见已处理或证据已足够支持结论时，不重复听读同一材料。

同一意见再次转来，先比较目标值与版本是否变化；有新证据、新版本或实质性异议才重新打开对应问题。无关疑点不自动变成本轮新任务；只有它直接破坏当前结论时才扩大并说明具体原因。

## 第七步：发布所有保留季及新季照片

**要做什么**：网站publisher从磁盘正式JSON发布完整game release，再逐季同步已有悍跳输入；保留人工结果，不在发布时重建覆盖。2026-10-29按用户授权先发布S21现有122条媒体档案，正式计分总局数与缺口后续复核；S21尚无悍跳复核输入，次数与成功率留空。照片有新增时加`--photos`。新季先适配照片输入，不能调用S22/S23固定输入生成器冒充已处理新季。

```powershell
.\.venv\Scripts\python.exe scripts/workflow.py plan --season S23 --stage publish
.\.venv\Scripts\python.exe scripts/workflow.py run --season S23 --stage publish --photos
```

**产物**：`masters_web`活动release、各季悍跳、`website/api/player_photos.json`及API侧`website/assets/player-photos/`。

**验收标准**：活动版本包含新季及全部旧季，已有悍跳输入绑定同一game release；未复核且无输入的赛季留空，不解释成零次。活动版旧季在本地缺失时停止。照片来自同季已核原图，别名有证据；无可靠照片者保留缺图原因。API代码／照片清单变更后重启API清缓存，Next构建不会刷新该缓存。底层单独`--season`／`--sample`会替换整份活动集，日常用统一入口。

计分复用共同规则，有明确差异再局部覆盖：现行基础分狼胜+1.5、好人胜+1、负-1，来源见[计分配置](../config/game_rules.json)；整季积分含决赛，冠军榜只计决赛周，跨季积分不合成冠军分。有证据的规则差异局部适配；悍跳按同人同局去重，成功未知不进分母。

## 第八步：验收、交付并确定下次续跑点

**要做什么**：运行发布预检和通用网站验收，规则变更另跑对应语义测试；记录实际完成步骤、产物、哈希、已知／未知、导入及发布回执、旧季保留结果与下一步。

```powershell
.\.venv\Scripts\python.exe scripts/workflow.py run --season S23 --stage verify
# 只检查API时
.\.venv\Scripts\python.exe website/check_publication.py --api-only

.\.venv\Scripts\python.exe scripts/workflow.py plan --season S23 --stage verify --bvid $bv
.\.venv\Scripts\python.exe website/check_publication.py --seasons S23 --bvid $bv --api-only
```

**产物**：源/API/页面验收报告、必要截图、照片覆盖与缺图原因、全库及原始资料备份、真实进度和恢复点。

**验收标准**：逐季局数、座位、日夜、票轮和选票与API一致；单季／跨季统计、悍跳绑定、照片及桌面／390宽页面通过；旧季局数与内容摘要保持。记录测试覆盖边界，不将未检查特殊规则当通过，也不要求无来源的新季照片硬凑100%。下一次能按报告从未完成步骤继续，无需空白任务表。

局部验收报告使用 `mode: partial`，完整验收使用 `mode: full`，不能互相替代；默认分别保存为`publication-acceptance-partial.json`和`publication-acceptance.json`。S23导入预检也按完整/局部保存不同报告，不覆盖完整验收。报告记录实际详情请求数、验收对局数、请求与阶段耗时；`--seasons`限制详情范围，`--bvid`进一步选择变化局。保留全局summary分页、活动版本、保留赛季和唯一性检查；选手统计核对可能仍需读取相关季正式资料，报告中如实注明范围。

前端改动时在`website/web`运行`npm run typecheck`和`npm run build`，再用`website/run.py --production`启动；Windows先停止占用本站standalone目录的进程。网站回退从`/api/v1/releases`取真实ID，执行`python -m website.api.publish --activate <真实ID>`并核各季悍跳；JCMS、磁盘及整库恢复另行处理。

清理先运行`python scripts/cleanup_data.py`预览引用保护和候选，再决定`--apply`。原媒体、正式档案、规则哈希、ASR分块、当前旁证和DB引用快照保留；运行环境、模型和数据库目录不删。
