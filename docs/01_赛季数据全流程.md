# 赛季数据全流程

日常只处理当前新增批次，入口见[增量流程](08_增量更新流程.md)。历史已完成对局直接复用最终 JSON；修订时才按受影响对局重新取源。

## 第一步：采集原始资料

用 `workflow.py run --season S23 --stage collect` 发现新增官方媒体和微博日期窗口。最终 `game.json` 中已登记的 BV/CID/分 P 代表已完成来源，不要求旧音频或转写仍在。微博完成区间使用 `data/sources/weibo_checkpoint.json`，当前批次原件保存在忽略目录。

## 第二步：核实当天嘉宾与每局座位姓名真实底牌

当前窗口读取本批完整文字、官方阵容和必要画面。复用正式姓名与照片映射；新选手据官方名牌补充。物理身份、个人胜利阵营和淘汰边分别处理，不以发言自称替代底牌。

## 第三步：整理日夜与票型

从真实开局、入夜和天亮恢复轮次，按版型固定槽位填本局实际记录。PK、重投分别保存；未知投向不能写成弃票。实际发生与规则资格分开，终局后没有行动窗口的事项不可记主动空过。依据[字段规范](02_字段证据与交叉复核规范.md)和[呈现规范](10_对局信息呈现规范.md)。

## 第四步：生成当前批次人工复核页

当前窗口保存候选、身份截图和连续复盘区间，执行 `workflow.py run --season S23 --stage review`。页面遵循[复核页规范](09_复核页面生成规范.md)。悍跳及是否成功由用户选择；未填写继续未知，不默认无人悍跳。

## 第五步：固化最终数据

用户确认后，`workflow.py ... --stage finalize --review-export <导出JSON>` 将本批结算和人工结果写入 `data/games/<赛季>/<局目录>/game.json`。有自由备注时，由当前窗口解释为结构化修订，使用 `--note-revisions` 交给预检。预检失败时报告具体字段；不覆盖其他局。

## 第六步：局部复核与意见核对

自主复核或核对外部意见时，先限定对局、字段和证据区域；沿具体冲突的直接依赖扩大，范围内问题有结论或明确缺口即收尾。外部建议只提供意见，只有用户明确接受才修改。旧局重开时从必要视频定位重新取源，不恢复历史推断过程。仅结构检查通过不表示每个字段都已人工确认。

## 第七步：本地导出与网站

最终 JSON → 共用统计 → 静态数据和网站。`workflow.py ... --stage export` 生成本地数据，`website/run.py` 启动本地预览。网站不读取数据库、旧转写、历史反馈或推导指纹。已有照片是稳定基线，按新增选手补图。上线只在明确要求同步静态网站时执行，见[静态发布](../website/static_publish/README.md)。

## 第八步：验证并结束批次

日常核对本批新增/修订局及受影响选手；规则或统计实现改变时运行对应回归。最终数据和必要来源齐备后删除本批截图、全文、候选、复核页和反馈，不保存整套验收副本或回执。长期只保留正式数据、必要来源、配置、照片和源码。
