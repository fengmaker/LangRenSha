# 增量更新流程

适用于S23继续比赛后的每日更新。沿用[赛季数据全流程](01_赛季数据全流程.md)的事实与规则要求，只处理尚未正式归档的新对局，复用已完成资料。用户自行打开窗口、选择模型，说“增量更新”即可启动；本文是当前对话助手的执行指令。

## 窗口触发指令

收到“增量更新”后，当前窗口助手直接执行以下流程：

1. 读取增量状态、正式对局索引和本地原件，确定新增正赛/决赛周范围。默认S23；用户已给日期或BV时按指定范围。
2. 核对线上录像和官方微博的缺口，采集缺少的原件。用户已明确说采集完成时先验本地来源，缺什么补什么；不重复采集已有完整文件。
3. 准备本局完整文字：优先已有中文字幕，包括平台中文AI轨；确无可下载中文轨时才复用完整转写或用现有Paraformer转写。
4. 当前窗口模型读取本局全文、对应官方微博及必要原图，按下文第二步整理座位、姓名、真实物理底牌、日夜行动、警徽和每轮逐人票型，保存候选、定位证据与具体缺口。模型由用户在窗口选择，不在提示词或脚本中固定。
   姓名复用既有已确认别名映射，微博账号不直接代替规范名；每轮从`input.json`的空白骨架复制槽位，只填本轮事实，避免把上一轮的行动、死亡或票型带入后续轮。
   第二步同时处理选手和照片：先按规范姓名查已有选手及图片绑定，已存在的直接复用并跳过；新出现的从已爬取的官方微博原图读姓名牌，新增选手记录并绑定图片。沿用现有照片索引和网站照片清单，不另建一套选手系统；来源信息随绑定保存，缺图或名字不清才列出缺口。
5. 复用既有结构和规则检查，按[复核页面生成规范](09_复核页面生成规范.md)生成逐局人工复核页，交付可打开的页面路径。日夜与票型共用[呈现规范](10_对局信息呈现规范.md)。

完成条件：每局事实已整理，未确定的信息保持未知；新选手已绑定微博照片或注明具体缺图。页面达到09的选材、版式和交互标准，提供单行悍跳人/成功选择、本局意见及JSON导入导出。生成后结束本阶段；用户另行明确要求应用、入库或发布时才继续第三步。

所有资料分析和后续复核备注解释均在当前对话完成。禁止调用`codex exec`、`incremental_ai.run_json`或通过其他CLI/API另起模型。现有`analyze_incremental.py`不带`--prepare-only`和`apply_incremental_review.py`非空备注分支仍包含旧CLI调用，不能直接用作本窗口的分析入口。采集、转写、校验和渲染等本地工具照常复用；不需要本机CLI模型登录。

## 本地工具

```powershell
Set-Location D:\langrensha

# 1. “增量更新”已授权采集本次新增原件，直接比较并补齐缺口
.\.venv\Scripts\python.exe scripts/update_incremental.py --season S23 --yes

# 2. 只准备本机输入，随后由当前窗口模型分析并生成复核页
.\.venv\Scripts\python.exe scripts/analyze_incremental.py --season S23 --prepare-only

# 3. 打开页面，填写每局备注并勾选“已复核”，然后导出JSON
Start-Process 'data/manual_review/S23_新增对局人工复核.html'
```

采集与分析可以分开续跑。`--prepare-only`只准备输入，不能当作已分析；当前窗口模型完成事实整理后，复用既有候选校验和规则推导，保存结果并生成页面。日常分析直接使用已有原件和绑定，不反复重算文件哈希、重核旧照片或额外跑全量来源审计；程序在意见导入、入库等写入边界保留必要的版本检查，结果只在实际失败时说明。

主环境为`.venv`，ASR仍用`.venv-funasr39`和现有模型。B站Cookie默认`.secrets/bilibili.cookies.txt`，微博默认`.secrets/weibo.cookies.txt`。登录失效时修复对应平台Cookie后续跑，不自动更换来源。

微博归档现用官网 `weibo.com` 的作者帖子列表、长文及详情路径，不再使用移动端 `m.weibo.cn/api/container/getIndex`。必须有官网认可的桌面端登录态；只在移动端登录并不保证官网接口可用。需要更新时运行 `.\.venv\Scripts\python.exe scripts/login_session.py weibo`，在打开的 `weibo.com` 正常登录，再回终端按Enter导出；完成后重跑采集，不必每次重新登录。

## 第一步：检查差距并确认采集

更新脚本每次重新读取目标官方合集，按BV、CID、分P与本机原件和正式档案比较。报告包括本地与线上录像日期、有效媒体数、新增对局候选、需采集项、历史正式来源的媒体缺口及来源冲突。媒体条目不直接等于正式对局数；标题中的日期、版型和局次仍是候选。

本日更入口只展示、统计和采集正赛/决赛周，表演赛不进入增量计数、媒体检查或新局队列；已有表演赛原件保留。赛事性质未知的来源仅单列范围缺口。

已有正式档案不进入新局分析队列。已采到原件但没有正式档案的新局仍进入队列，不会因为先前刷新过合集计划而漏掉。同一录像来源改变CID时明确报告，不能覆盖原来已确认的来源。未知赛事性质或未适配版型保留具体缺口，不套用旧季规则。

微博限定在本赛季窗口内官方UID`7525583841`的可见发布。脚本按本地归档的请求范围和完整覆盖，找出赛季开始至北京时间今天之间尚未覆盖的日期；已有完整窗口直接复用，已完成但当天尚未闭合的窗口会补扫最后一天，未完成窗口按原日期续跑。此前S22归档只在与S23日期范围重叠处提供覆盖，不会扩大S23起点。默认目标日是北京时间今天。

微博报告分别显示本地归档请求的最大日期、本地最新帖子日期、连续完整覆盖，以及待补日期缺口和待扫描/恢复窗口。最新帖子日期不能证明中间日期已经采齐；没有发帖的日期也不构成帖子缺失。确认前不请求微博数据；确认后从官方网页帖子列表采集窗口，新增帖子数量在采集后统计。登录受限或页面不可读时，保留失败窗口供重跑，不自动切换接口。旧移动端游标的未完成窗口会迁移到新的`*_desktop`目录，并复用原帖子文件；旧目录保留。已被其他完整归档的合并范围覆盖的旧未完成记录不会重复排入，与原接口无关。

```powershell
# 检查B站在线合集与本地微博窗口差距，不采集、不提示确认、不保存增量状态
.\.venv\Scripts\python.exe scripts/update_incremental.py --season S23 --check-only

# 明确指定微博日期范围，起止日都包含；仍会提示确认
.\.venv\Scripts\python.exe scripts/update_incremental.py --season S23 --since 2026-10-21 --until 2026-10-29

# 明确授权本次采集，省略终端确认
.\.venv\Scripts\python.exe scripts/update_incremental.py --season S23 --yes
```

先下载有效中文字幕，包括平台中文AI轨。有中文轨就不取音频；正常请求明确无可下载中文轨才取独立音轨。查询失败、需登录、中文轨下载失败都不能解释成无字幕。现有完整字幕/音轨复用；失败项保留，重新运行后续接。采集阶段不运行ASR，不登记数据库。

微博窗口只有在网页帖子列表扫描结束、日期可解析、长文展开及配图完整时才算完成。默认目标为今天；今天尚未结束时按既有覆盖规则保守处理，次日仍会补扫尚未闭合的最后一天，不能因已有窗口而永久漏掉当天后续发布。

完整日覆盖按实际扫描时间判断：即使历史目录写着截至10月20日，如果它在10月20日尚未结束时采集，脚本仍会补扫最后一天。补扫复用已有帖子，保留原件。用户确认前不会访问微博；确认后若官方网页列表要求登录或不可读取，会报告窗口失败并保留状态，处理平台访问问题后重跑同一命令，不自动重试或切换接口。

## 第二步：AI预处理及人工复核

分析只选择增量队列内原件就绪、尚未应用的正赛/决赛周。已完成候选复用，失败局重跑；某局缺原件只阻塞该局，其他就绪局可以继续。首次不指定BV时生成完整待复核新局页面；指定BV生成单独页面，不覆盖其他新局的复核工作区。

处理顺序：

1. 按本局BV/CID复用已采文字。已有中文字幕优先；没有中文轨且没有完整转写时才运行Paraformer。
2. 阅读完整字幕/转写，定位连续法官复盘和必要画面。复盘可能在中段，不固定取片尾；按需调用既有截图工具取得姓名牌、真实身份及有歧义的票型证据。
3. 整理12席座位、规范姓名和物理底牌，同时完成新选手的微博照片绑定，已有选手直接跳过；再整理日夜行动、死亡/离场、警徽和逐轮逐人票型。完整保留PK与技能重投；未知不当成弃票、空过或平安夜。
4. 运行既有结构检查和本局规则推导，解决具体矛盾，保存最终结果。内部定位资料保存在本机；悍跳按用户意见处理。
5. 按[09 复核页面生成规范](09_复核页面生成规范.md)生成新增及此前未完成新局的离线逐局页面：身份截图置顶，展示座位身份和统一对局流程，投票穿插在对应阶段；转写截取连续复盘区间，保留本局复核意见。

使用`game_review_page.py`和[09](09_复核页面生成规范.md)约定的`review_display.json`生成页面；逐局展示序列由`game_timeline.build_game_timeline`统一生成，常规事项和特殊版型的具体条件集中维护在[10](10_对局信息呈现规范.md)。

复核页面与待核清单统一保存在`data/manual_review/`，从[人工复核首页](../data/manual_review/index.html)查看；历史槽位与新增对局各有入口，导出的反馈保存到其中的`feedback/`。

```powershell
# 只准备指定新局输入（需先由更新入口发现并采集）
.\.venv\Scripts\python.exe scripts/analyze_incremental.py --season S23 --bvid BV实际编号 --prepare-only

# 只准备本机文字输入，不调用AI或抓图，不生成假分析结果；缺文字时仍可能运行ASR
.\.venv\Scripts\python.exe scripts/analyze_incremental.py --season S23 --prepare-only

# 只有确需CPU转写时显式指定；已有完整文字不会因此加载ASR
.\.venv\Scripts\python.exe scripts/analyze_incremental.py --season S23 --device cpu --prepare-only
```

页面每次查看一局，用一行控件选择悍跳人及是否成功，其他修正写本局备注，例如：

> 3号姓名改为XXX；第一天夜晚女巫没有用毒；第一天5号投给7号。猎人是否开枪仍不确定。

备注为空且勾选表示接受当前事实候选；悍跳按实际填写的结论处理，空白项保留既有结果。仅应用已勾选的局；草稿和意见文件见[09](09_复核页面生成规范.md#意见文件与应用)。

## 第三步：应用备注、入库与发布

将浏览器导出的JSON保存到`data/manual_review/feedback/`，例如`S23_逐局复核意见.json`，交给当前窗口助手。v2的悍跳选择由应用器直接转成结构化结果，不调用模型；自由备注由当前模型解释，保存结构化修订和原备注，先生成应用预览，列出具体差异及尚未解决的歧义。复用现有版本检查、缓存、事务、备份及发布机制；原自动CLI备注分支不再使用。用户明确要求应用、入库或发布后，按其授权范围执行。

空备注直接接受原候选；非空备注由AI按用户指定范围转换为结构化修订，保留原备注与修改前后差异。不能把备注原封不动复制到JSON后声称已修正，也不能静默改动未提及的历史事实。含糊项会明确列出；用户明确表示某字段未知时保留未知，执行指令无法判定时不擅自写库。悍跳只取用户明确填写的结论，空白不能当成无人悍跳。

预览会保存备注修订及规则推导的本机缓存，并输出具体修改、未知和悍跳处理结果；同一版本执行`--apply`时复用该结果。在尚未写库前修改备注，会重新准备本局预览；已写库后的不同备注会明确要求作为修订处理，不能静默覆盖已应用结果。

应用前核对原件、候选与导出版本，备份数据库，登记本局来源。日夜档案与完整票型共享本局事务；只替换本次已确认局，保留其他局/赛季。正式文件写入`data/games/S23/`，候选、原备注、修订及证据保留在增量目录。无需修改原75局历史快照或假装新局属于旧授权范围。

网站沿用统一发布入口，发布包含全部保留季的完整game release，再同步人工悍跳输入和照片。照片准备按当前正式档案姓名读取既有确认记录及增量名牌索引，保留已有照片；清单更新后重启API清缓存，核对新增选手页面和图片地址。入库成功与发布成功分别记录：发布失败可在相同导出文件上重跑`--apply --publish`续接，不能重做AI分析或覆盖人工结果。发布后对变化BV做验收；局部验收不冒充全季逐字段复核。

## 文件与续跑点

| 文件/目录 | 用途 |
| --- | --- |
| `data/reports/S23/incremental/state.json` | 新局采集、分析和应用进度，微博完整窗口及失败信息 |
| `data/extractions/S23/incremental/<BV>_pNN_cid<CID>/` | 单局文字输入、截图计划与证据、当前窗口整理的候选及规则推导 |
| `data/manual_review/index.html` | 人工复核统一入口 |
| `data/manual_review/S23_新增对局人工复核.html` | 本次交付的逐局人工复核页 |
| `data/manual_review/feedback/` | 用户导出的复核意见JSON |
| `data/reports/S23/incremental/analysis.json` | 本次实际分析数量、失败、待采集项及页面位置 |
| `data/raw/bilibili/`、`data/raw/weibo/` | 原始媒体/字幕/微博，沿用原件目录 |
| `data/games/S23/` | 仅应用已确认结果后新增的正式档案 |

日常不用重新执行整季`workflow collect/review/import`。修改导入器、规则或迁移时，才按风险运行对应回归；完成新增范围和相关验证即可收尾。
