- [进度与缺口](../data/reports/S22_投票补录进度.json)：记录无票型局、未知日序与未知类型，不将“没有提取到”写成“没有投票”。
- [逐局核对报告](../data/reports/S22_投票逐局核对.json)、[待复核清单 CSV](../data/exports/S22_投票待复核清单.csv)：按比赛日期、局次和游戏日列出疑问、缺口、原文及视频时间。

离线页左侧可同时选择比赛日期、问题状态和游戏日。日期显示疑问及待复核数量，局卡片显示具体哪一天有问题。“下一局”遵循当前筛选。每局的“投票核对清单”区分冲突与资料缺口，支持逐项填写人工意见、定位原文、按时间打开原视频及查看内嵌截图。

“有疑问”包括原文冲突、票权或日序矛盾、阶段不明；“待补录 / 复核”包括缺票、缺名单或尚未确定完整票权。逐局结构检查、文字核对与原视频截图查看分别记录，不自动等同于人工确认。

## 业务记录与证据

每局的 `voting.json` 是独立投票业务档案，关联同目录 `dossier.json` 的 `slug`。上警/警下名单指最初竞选报名；每轮最终候选人另记，不能把退水后的候选人补集当作初始警下名单。名单有完整明确播报时才生成完整座位划分；无法辨识的人名、号码、名单片段保持未知。

每轮记录游戏日、警徽/放逐类型、同日轮号、首轮/PK后/其他重投阶段、候选人、已知票权名单、逐人投向、明确弃票、未记录票、平票名单和明确公布的当选或出局座位。PK 首轮与复投分别保存；不计算票数来反推赢家，也不从最终放逐对象倒推各人投向。警长半票等权重暂不计算。

`partial` / `complete` 只表示相对于已知票权名单的完整度。票权本身未知时必须为 `partial`。未知票不产生弃票记录。存在冲突、目标不在明确候选池或数字粘连时保留原文待核，不擅自纠正号码。自爆后明确入夜可记录该日中断，但未提取到投票不能证明自爆前从未投票。

原文、时间范围、来源哈希、日序锚点、额外推断锚点和疑点另存 `data/extractions/S22/voting/{BVID}.json`。这些材料不写进业务表。机器稿提取尚未人工回听，完整度也不等于事实已经确认。

经核对接受的更正保存在 `data/extractions/S22/voting_review/accepted.json`，包含来源哈希、更正前后字段、理由和原句；重新提取后会按来源及轮次时间定位重新应用。原文或轮次不再匹配时停止应用该更正，避免套到别轮。原视频查看结论及截图记录在同目录 `video_checks.json`，画面不足以确定的票继续保留待核。

## 数据库

迁移为 `009_voting_records.sql`，四张补充表与 `games.id` 关联：

| 表或视图 | 用途 |
| --- | --- |
| `game_sheriff_registrations` | 各次报名的上警/警下座位 |
| `game_ballots` | 每天、每种投票、每轮的候选、票权、阶段与公布结果 |
| `game_ballot_choices` | 每轮逐人投向或明确弃票 |
| `game_voting_days` | 每个已知游戏日的覆盖与自爆中断状态 |
| `current_game_votes` | 联结日期、局次、游戏日与逐人票型的查询视图 |

本次全文补录使用新表；`game_event_votes` 保留为原固定事件模型的历史入口，没有再复制同义数据。原档案与既有规则对齐的哈希继续保留。重新导入 `dossier.json` 不会删除独立投票记录。投票重导入以单局事务替换，重复执行不会累计选票；删除对局时补充记录随之删除。

```sql
SELECT slug, event_date, game_number, day_number, kind, ballot_number,
       stage, voter_seat, target_seat, state
FROM current_game_votes
ORDER BY event_date, game_number, day_number, kind, ballot_number, voter_seat;
```
